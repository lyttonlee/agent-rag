## 1. 结论速览（TL;DR）

| 问题 | 结论 |
|---|---|
| 长短切分模式叫什么 | **Small-to-Large（父子块）检索**，工业界三种变体，推荐"变体 B：条件注入"（精确匹配用户需求，见 §2） |
| LangChain 有完整方案吗 | **有模式，不引框架**：`ParentDocumentRetriever`（检索小块/返回父块）+ 文本切分器。但其 docstore 生产化需 Redis/Mongo、依赖树重（~50MB），与本项目单库 PG 架构、密级下推、SSE 事件契约冲突（见 §3.1、§4 方案一） |
| LlamaIndex 有完整方案吗 | **有模式，不引框架**：`HierarchicalNodeParser` + `AutoMergingRetriever`（兄弟块命中 ≥50% 自动上卷父块），依赖 ~171MB 且耦合其 Node 体系（见 §3.2） |
| 有轻量专用库吗 | **有：chonkie**（MIT、505KB、Rust 内核、token 精确计量、支持注入自定义 tokenizer、56 语言含中文）。**推荐作为切分尺寸引擎引入**（见 §3.3） |
| 最终落地架构 | **方案二（混合）**：chonkie 做 token 计量/硬切 + 保留自有公文段落/条款单元提取（领域优势）+ PG 单库自建父子存储与条件注入检索（见 §4） |
| 性能代价 | 小切片向量数约 ×2.5–3.5（7.9GB → 19–27GB，halfvec 可减半）；Embedding 2.7h → 约 3–3.5h；检索 p95 预计 +5–15ms；生成 token 需预算管控（见 §6） |
| Agent 用 LangChain/LangGraph 吗 | **不迁移**。现有 agent 是 <1100 行固定管线（意图路由→规划→执行→聚合），行业共识此类线性场景自研循环更优；迁移将丢失 SSE 契约/审计/密级耦合/ModelProvider 抽象（见 §10） |
| 最大硬风险 | 6.49 服务器内存能否容纳 480–680 万向量的 HNSW 常驻（见 §8-R1，需用户确认） |

## 2. 模式定义与三种变体对比

### 2.1 要解决的矛盾

检索粒度与生成粒度是同一个矛盾的两面：

- **大切片**（800–2000 token）：上下文完整，但 embedding 信号被稀释，主题级查询召回下降（"向量路 top1 距离变大"），且不相关内容被一起拖入；
- **小切片**（100–200 token）：匹配精准，但切片常缺主语、缺前提（公文尤其明显——"第二条"离开了"第一章 总则"就无法理解），LLM 生成时依据不足。

父子块模式把两者解耦：**小块用于检索（进向量/BM25 索引），大块用于生成（命中后回表取父块）**。

### 2.2 三种变体

| 维度 | 变体 A：必返父块<br>（LangChain ParentDocumentRetriever） | 变体 B：**条件注入**<br>（本报告推荐） | 变体 C：兄弟自动合并<br>（LlamaIndex AutoMergingRetriever） |
|---|---|---|---|
| 机制 | 命中小块 → 无条件返回其父块 | 命中小块 → 先返回小块；**仅当"上下文不足"信号触发时**注入父块 | 命中小块 → 若同一父块的兄弟块命中比例 ≥ 阈值（默认 50%），上卷为父块 |
| 上下文完整度 | 高（恒定） | 中→高（按需） | 中→高（按命中聚集度） |
| token 消耗 | 恒定高（top_k × 父块大小） | **低（仅触发时）** | 中（聚集时合并反而省 token） |
| 精准度 | 低（引入无关上下文） | **高（公文引用要精准）** | 中 |
| 实现复杂度 | 低 | 中（触发信号设计，可复用现有 `is_no_useful_info` 信号体系） | 高（依赖层级树与阈值标定） |
| 与 query 改写协同 | 弱 | **强（改写重检仍不足才注入父块，形成多级兜底）** | 中 |

**选型理由（变体 B）**：与用户需求原文"如果上下文缺少，查询匹配自身块的大块注入"逐字对应；公文场景对引用精准度敏感（"宁缺毋滥"是既定红线），无条件返回父块会把无关条款拖进生成上下文；条件注入与已交付的"无有用信息"双信号判定（`policies.is_no_useful_info`）、以及检索优化方案中的 query 改写构成**三级兜底链条**：

```
改写重检（P2）→ 仍不足 → 父块注入（P1）→ 仍不足 → 拒答/任务型兜底（已上线）
```

变体 C 的"兄弟合并"作为 **P3 可选增强**（其去重价值：top_k 个小块常来自同一父块，合并后反而省 token——这一点会被 B 的父块注入自然覆盖大部分，故列可选）。

## 3. 生态调研：有没有现成方案

### 3.1 LangChain（模式可借鉴，框架不引入）

**现状（2026-10 官网/文档核实）**：

- `langchain_text_splitters.RecursiveCharacterTextSplitter`：按**字符**递归切分（分隔符优先级 paragraph > line > sentence > word），需传 `length_function` 才是 token 精确；`SentenceTransformersTokenTextSplitter` 在 `langchain-experimental` 实验包，API 不稳定。
- `langchain.retrievers.ParentDocumentRetriever`：标准 small-to-large 实现——child_splitter 切的小块进 vectorstore，parent_splitter 切的大块进 docstore；检索命中小块后按 parent_id 回 docstore 取父块。
- 官方与社区文档明确：docstore 生产化用 `RedisStore`/`MongoDBStore`（InMemoryStore 重启即丢）。

**评估**：

| 优势 | 劣势（对本项目） |
|---|---|
| 模式成熟、文档多、即插即用 | 需额外引入 docstore（Redis/Mongo）——**破坏"PG 单库统一元数据+BM25+向量"的锁定决策** |
| 切分器开箱即用 | 依赖树重（langchain-core + pydantic 版本约束链，~50MB），内网离线环境安装面大 |
| — | 检索器与我们的**权限下推**（服务端 WHERE 密级/scope）、**SSE 事件契约**、**ModelProvider 抽象**（本地 Qwen 内网端点）全部需要适配层，框架收益被抵消 |
| — | 多一个组件（docstore）就多一个故障点/备份点，运维台也要改 |

**结论**：模式 = 变体 A 的标准参考实现，**借鉴其父子 ID 设计；框架不引入**。

### 3.2 LlamaIndex（模式可借鉴，框架不引见）

- `HierarchicalNodeParser.from_defaults(chunk_sizes=[2048, 512, 128])`：一次切出多级树（大→小），仅叶子节点进向量索引；
- `AutoMergingRetriever(base, storage_context, simple_ratio_thresh=0.5)`：叶子命中同父比例 ≥50% 时换父块（变体 C 原型）。

**评估**：`SentenceSplitter` 默认按 token 切分较严谨；但 LlamaIndex 依赖 ~171MB，且其 Node 类型体系（`parent_node`/`child_nodes`/docstore 强约束）与我们的 `Chunk` ORM 模型、zhparser BM25、权限冗余列体系不兼容。**结论：借鉴其阈值合并思想（进 P3 备选），框架不引入。**

### 3.3 chonkie（推荐引入的专用切分库）

- 定位：**只做切分**的轻量库（chonkie-inc，MIT 协议，PyPI 可装），Rust 内核 + Python 封装，wheel 505KB；
- 能力：`RecursiveChunker` / `TokenChunker` / `SentenceChunker` / `SemanticChunker` / `LateChunker` 等 10 种切分器；**默认 token 精确**（`tokenizer_or_token_counter` 可指定 tokenizer 或自定义计数函数——可传入 Qwen tokenizer 计数，与 embedding 模型严格对齐）；56 语言含中文；
- 性能：官方基准 token 切分 4.82 MB/s，较 LlamaIndex 快 ~50×（对本项目 44GB 原文是分钟级 vs 小时级差异，但切分本身不是瓶颈，此项非决定因素）；
- 父子模式：无内置（本就用我们的 PG 存储实现，见 §5）。

**已核实的风险（第三方实测报告，2026）**：项目较年轻；部分场景 `start_index` 返回 -1（表格类内容 offset 丢失）。**本项目只用其文本与计数，不依赖 offset**，且切分结果进评测门禁（§9），风险可控。

### 3.4 自研切分（现有 chunker）

现有 `chunker.py` 的独特价值必须保留：

- `_SECTION_RE` 识别公文条款结构（`第X条`/`一、`/`（一）`/`1.`/`A、`）——**这是 LangChain/chonkie 通用切分器都没有的领域能力**，公文检索质量的核心依赖之一；
- 上下文前缀（标题｜机关｜日期）拼接；
- 段落/句/条款/定长四策略 + 尾重叠机制（用户明确要求保留）。

短板：按**字符**切分（中文 1 字 ≈ 0.6–1 token，随文本波动），要做 100–200 **token** 级小切片需要 token 级计量。

### 3.5 生态对比总表

| 库 | 体积 | 尺寸单位 | token 精确 | 父子模式 | 中文/公文结构 | 框架耦合 | 本项目用途 |
|---|---|---|---|---|---|---|---|
| LangChain splitters + ParentDocumentRetriever | ~50MB | 字符（默认） | 需 length_function | ✅（docstore 另需 Redis/Mongo） | 通用分隔符 | 重 | **仅参考** |
| LlamaIndex HierarchicalNodeParser + AutoMerging | ~171MB | token | ✅ | ✅（Node 体系强约束） | 通用 | 重 | **仅参考** |
| chonkie RecursiveChunker | 505KB | token（默认） | ✅（可注入 Qwen tokenizer） | ❌（切两次即可） | 56 语言通用 | **零** | **引入：尺寸引擎** |
| 自研 chunker（现有） | 0 | 字符 | ❌（需补计量） | 自建 | ✅ **公文条款识别（独有）** | 零 | **保留：单元提取** |

## 4. 落地方案对比与推荐

### 方案一：全盘引入 LangChain/LlamaIndex（切分 + 检索 + agent 一体）

- **做法**：用 ParentDocumentRetriever 替换 `hybrid_retrieve`，agent 迁 LangGraph。
- **否决理由**：① docstore 破坏单库锁定决策；② 权限下推要在框架检索器外层包过滤，密级过滤点从 SQL 层退到应用层，违背"检索阶段下推"红线；③ SSE 事件序列（meta/plan/step/token/done）需重映射；④ ModelProvider（本地 Qwen 内网端点、启动自检）要重写适配；⑤ agent 迁移丢审计与安全耦合（详见 §10）；⑥ 内网离线安装体积与版本约束风险。**框架收益（600+ 工具生态、LangSmith）在私有内网 + 本地模型场景为零。**

### 方案二：混合架构（推荐）

```
┌───────────────────────── 入库（ingestion）─────────────────────────┐
│ 原文 → 去噪 → 单元提取（自有：段落/条款/句子，保留）                  │
│   → 小块合并（100–200 token，chonkie token 计量 + 尾重叠保留）       │
│   → 大块合并（800–2000 token，同左，独立粒度）                       │
│   → 小块：embedding + tsvector + 落库（granularity=small）          │
│   → 大块：纯文本落库（granularity=large，parent_id 反向挂小块）     │
└──────────────────────────────────────────────────────────────────┘
┌───────────────────────── 检索（hybrid_retrieve）──────────────────┐
│ query → 向量 + BM25（仅查 granularity=small，索引不变样）            │
│   → RRF → rerank → top_k 个小块（引用展示仍为小块，精准）            │
│   → 【条件注入判定】上下文不足信号触发？                            │
│       否 → 直接返回小块（现状行为，零额外成本）                      │
│       是 → 按 parent_id 回表取大块（主键 IN，亚毫秒）                │
│           → 去重（多小块同父只注入一次）→ 注入生成上下文             │
└──────────────────────────────────────────────────────────────────┘
```

- **技术复用点**（对应用户"注意技术复用"）：chonkie = 通用切分能力（token 计量、兜底硬切）用成熟库；自有 chunker = 领域结构识别保留；ConfigKV = 配置存储复用；visibility filter = 父块权限过滤复用同款 WHERE 构建。
- **为什么不是"纯自研"（方案三）**：token 精确计量自写≈重新实现 chonkie 核心功能（违背"万不得已不造轮子"）；除非 chonkie 内网安装受阻，回退方案 = 直接用 `transformers` 加载 Qwen tokenizer 写一个 ~15 行计数函数（仍是"用官方 tokenizer"，非造轮子）。

### 方案三：纯自研扩展 chunker（回退方案）

不引任何新依赖，自写 token 计数（transformers AutoTokenizer）+ 父子存储。可行、但违背库优先原则，且失去 Rust 性能与社区维护。**仅当 chonkie 无法安装时启用。**

## 5. 详细设计（方案二）

### 5.1 Schema 变更（零新组件，PG 单库内完成）

`chunks` 表新增两列（alembic 迁移）：

| 列 | 类型 | 说明 |
|---|---|---|
| `granularity` | `varchar(8)` default `'small'` | `small`=检索单元（有向量/tsvector）；`large`=生成单元（纯文本，向量与 tsvector 均为 NULL） |
| `parent_id` | `varchar(32)` FK→chunks.id, nullable | small 指向其 large 父块；存量切片为 NULL（迁移期兼容） |

设计要点：

1. **大块不占向量、不占 tsvector**——存储只增文本，向量增长仅来自"小块变小、数量变多"；
2. 大块行同样冗余 `security_level / permission_tags / space_id`（与现有小块一致），**父块注入时权限过滤与小块完全同构**（复用 `build_visibility_filter`），不引入新的越权面；
3. 不建独立父块表：检索期"小块→父块"是同表主键回表，且未来若需父块级过滤/统计，单表 WHERE 更简单；
4. HNSW 索引不变（只索引 small 行——向量列为 NULL 的行天然不入索引）。

### 5.2 切分层（chunker.py 扩展，保留全部现有能力）

```python
# 新签名（向后兼容：默认走原单粒度路径）
def chunk_document_dual(
    text: str, prefix: str,
    strategy: ChunkStrategy = "paragraph",
    small_max_tokens: int = 150,      # 配置中心 retrieval.small_max_tokens
    small_overlap_tokens: int = 20,
    large_max_tokens: int = 1200,     # 配置中心 retrieval.large_max_tokens
    large_overlap_tokens: int = 100,
    token_counter: TokenCounter = qwen_token_counter,  # chonkie 注入
) -> tuple[list[Chunk], list[Chunk]]:
    """双粒度切分：返回 (小块列表, 大块列表)。

    小块与大块独立切分（互不嵌套对齐），落库时小块按 seq 就近挂父块：
    小块 [start,end] 与父块 [start,end] 重叠比例最大者为 parent。
    """
```

要点：

1. **单元提取（段落/条款/句子）与重叠机制原样保留**——大块就是"放大 max_chars 的现有逻辑"，小块是"缩小 max_chars 的现有逻辑"，一套代码两个参数；
2. token 计量：首选 chonkie `RecursiveChunker(tokenizer_or_token_counter=qwen_counter)`；`_hard_split` 的兜底硬切同步 token 化；
3. 父子挂载用**字符偏移重叠比例**（不要求小块严丝合缝嵌在大块内——两套独立切分的边界天然错位，强行对齐会牺牲段落/条款边界质量）；
4. 前缀处理优化：入库文本 `content` 保留"前缀+正文"（检索质量依赖），但 **embedding 输入与小块注入文本分离**——嵌入用 `prefix+body`（保持现有召回行为），生成注入时大块正文前只拼一次文档级前缀（避免 top_k 个小块各自带前缀造成的重复堆叠）。

### 5.3 检索层：条件注入（retrieval.py 扩展）

**触发信号**（复用现有信号体系 + 一个新信号，全部配置中心可调阈值）：

| 信号 | 来源 | 含义 |
|---|---|---|
| `citations 为空` | 现有 | 无任何命中 |
| 双信号异常（向量距离 > 阈值 且 关键词零命中） | 现有 `is_no_useful_info` | 语义+词汇双维度判死 |
| **rerank top1 < rerank_min_score**（P2 交付后启用） | 新增弱相关信号 | 有命中但都弱相关——**这是父块注入的主场景** |

**注入逻辑**：

```
top_k 小块（≤8）→ 收集 parent_id 集合（去重，≤ parent_inject_max_count，默认 2）
  → 回表 SELECT content FROM chunks WHERE id IN (...) AND granularity='large'
    AND <visibility_filter>   # 父块权限二次校验（双保险）
  → 注入生成上下文（受 parent_inject_max_tokens 总预算约束，默认 3000）
  → 超预算时按小块 rerank 分排序截断
```

要点：

1. **父块权限必须二次校验**：虽然父块行冗余了密级/权限列（入库时与文档一致），但注入路径独立成链，单测必须覆盖"父块密级高于调用方额度 → 不注入"（防未来入库逻辑改动引入越权）；
2. 注入的大块**也进入引用列表**（Citation 增加 `via_parent` 标记），前端可展示"上下文已扩展至父块"，审计可追溯；
3. **性能**：回表是主键 IN 查询（≤2 行），p95 增量 <5ms；去重后注入的大块数 ≤2，token 预算硬上限防上下文膨胀；
4. **不改变拒答红线**：注入父块后仍判"无有用信息"的，走既有拒答/任务型兜底，**不因注入而放松阈值**。

### 5.4 配置项（配置中心 retrieval 类，启动种子，前端"检索参数"页签已就绪）

| key | 默认 | 说明 |
|---|---|---|
| `small_max_tokens` | 150 | 小块 token 上限（100–200 区间可调） |
| `small_overlap_tokens` | 20 | 小块重叠 |
| `large_max_tokens` | 1200 | 大块 token 上限（800–2000 区间可调） |
| `large_overlap_tokens` | 100 | 大块重叠 |
| `dual_granularity_enabled` | true | 总开关（关 → 退回单粒度 800 字符现状） |
| `parent_inject_enabled` | true | 条件注入开关 |
| `parent_inject_max_count` | 2 | 单次最多注入父块数 |
| `parent_inject_max_tokens` | 3000 | 注入父块总 token 预算 |
| `parent_inject_min_rerank` | 0.35 | 复用 rerank_min_score 语义：rerank top1 低于它才注入（P2 后生效） |

> 单位约定：配置一律 **token**（与 embedding 模型对齐），代码注释与文档明示"1 汉字 ≈ 0.6–1 token（Qwen tokenizer 实测区间）"，单测锁死换算，杜绝字符/token 混淆。

### 5.5 迁移方案（存量 193 万切片）

| 路径 | 做法 | 代价 | 适用 |
|---|---|---|---|
| **B（推荐）** | 保留存量 800 字符切片为 small 层，**仅回填 large 层**：对每篇文档按 large 参数补切大块、存量小块 `parent_id` 就近挂载 | 只 embed 大块？**不，大块不 embed**——零 embedding 耗时，仅一次文本回填（小时级） | 存量平滑过渡，新文档双粒度 |
| A | 全量重新入库（重跑 44GB 原文 + 重新 embedding 3–3.5h） | 高 | 需要把存量小块也切成 100–200 token 时 |

推荐 **B 先行、A 按文档自然更新时机执行**（新入库文档默认双粒度；存量文档在被编辑/替换时自动重切）。理由：B 立刻拿到"上下文完整性"收益（父块注入），把"小块化"的向量增长（§6）变成可控的渐进过程，避免一次性 3 倍向量扩容冲高 6.49 内存。

## 6. 性能测算（20 万文档基线：原文 44GB、193 万切片、向量 7.9GB、Embedding 2.7h）

| 指标 | 现状 | 方案二（小块 100–200 token） | 说明 |
|---|---|---|---|
| 切片总数 | 193 万（~800 字符） | **480–680 万** small + 100–200 万 large | 小块变小数量 ×2.5–3.5 |
| 向量存储 | 7.9GB（1024 维 float32，4KB/条） | **19–27GB**（仅 small 有向量）；large 纯文本 | **最大代价项**；pgvector 0.8 已装，**halfvec 可减半至 10–14GB**（召回损失需评测，通常 <1%） |
| 文本存储 | ~44GB（含前缀） | ~90–130GB | large 层使正文约存两份 |
| Embedding 耗时 | 2.7h | **约 3–3.5h** | 总嵌入 token ≈ 原文 token + 前缀重复开销（前缀 ~25 字/块 ×3 倍块数，占比 <2%）；**large 不 embed** |
| 入库耗时 | 基准 | +切分两次（毫秒级/篇）+ large 落库（batch insert） | 增量可忽略 |
| 检索 p95 | 基准 | **+5–15ms** | 索引行数 ×3 → HNSW 查询 O(log N) 增长极小；回表主键 IN 亚毫秒；`ef_search` 可调 |
| 生成 token | top_k × 800 字符 | 小块路径不变；**仅触发时** +≤3000 token 预算 | 预算硬顶 + 去重，防膨胀 |
| HNSW 常驻内存 | ~8GB 级 | **20GB+ 级（halfvec 后 ~12GB）** | **需确认 6.49 服务器 RAM（§8-R1）** |

**性能设计红线**（对应用户"注重性能"）：① large 不 embed（省 2/3 嵌入算力与存储）；② 条件注入非常驻（无信号触发时零开销）；③ 注入预算硬顶；④ halfvec 作为存储缓解的评测项而非默认（避免未评测先改精度）。

## 9. 验收标准与评测方法

**评测集**（沿原方案）：50–100 条真实 query（含已知失败 case——**仍希望用户提供一批真实失败 query，这比合成数据有价值得多**），标注 gold 切片。

| 指标 | 现状基线 | P1 目标 | P2 目标 |
|---|---|---|---|
| recall@8（gold 在 top8 比例） | 待评测台首测标定 | **+10–15 个百分点** | +15–20 |
| 救回率（原失败 query 被救回比例） | — | ≥50% | ≥65% |
| 检索 p95 延迟 | 首测标定 | 增幅 ≤15ms | 增幅 ≤40ms（改写多轮有超时预算） |
| 生成上下文 token 均值 | 首测标定 | 增幅 ≤30%（预算内） | 同左 |
| 权限越权用例（父块注入路径） | 0 | **0（硬门槛）** | 0 |

方法：评测台对同 query 并行跑"现状单粒度"与"双粒度+注入"两条链路，比对 recall/延迟/token 三列；参数组合（小块尺寸 × 注入阈值）网格扫描后取帕累托最优点。

## 10. Agent 侧：是否可用 LangChain 技术

**结论：不迁移，保持自研管线；可评估的局部复用均不划算。**

现状：`app/services/agent/` 共 7 文件 ~1100 行——router（意图分类，LLM+规则兜底）→ planner（步骤规划）→ executor（步骤执行）→ aggregator（复杂任务汇总）+ policies（双信号拒答判定）+ config（ConfigKV 驱动）。工具面只有 2 个：retrieve、generate。

行业共识（2026 多篇生产复盘一致）：<5 工具、线性 think-act-observe 流程，100–300 行自研循环是更优解；LangGraph 的价值在真实分支（≥3 条有意义路径）、持久化断点、多 agent 协作——本项目均不具备。

| 维度 | 迁 LangChain/LangGraph | 保持自研 |
|---|---|---|
| SSE 事件契约（meta/plan/step/token/done） | 需在框架外重包一层，框架黑盒化增加调试成本 | 原生一一对应 |
| 密级/权限下推 | 框架检索器外层包过滤，违背 SQL 层下推红线 | SQL 层原生 |
| ModelProvider（本地 Qwen 内网端点、启动自检拒云端） | 需自写 ChatModel 适配器 | 原生 |
| 审计（actor/trace） | 需接 LangSmith（**内网不可用**）或自埋点 | 已有 audit 服务 |
| 依赖 | +50MB（langchain）/~171MB（llama-index），内网离线安装面 | 0 |
| 生态收益（600+ 工具、LangSmith） | **私有内网+本地模型场景价值为零** | — |

**重评触发条件**（写入架构决策记录）：出现以下任一且稳定 2 个迭代以上，再评估 LangGraph——① ≥3 条有意义的分支路径；② 需要跨重启/跨天的持久化断点（human-in-the-loop 审批）；③ 多 agent 角色协作（规划/执行/评审分离且互不重叠）。

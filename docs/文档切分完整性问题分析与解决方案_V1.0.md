# 文档切分完整性问题分析与解决方案报告（V1.0）

> 现象：入库选了「按段落切 + 有重叠区域」，但结果每块仍固定在小块 150 / 大块 1200，且**一个完整段落/条款被切断**，检索与生成上下文都丢失完整性。
> 本文分析当前流程、定位根因，并给出分阶段解决方案。

---

## 1. 结论先行

**当前行为不是 bug，而是「按 token 预算切分」的固有语义与用户「按段落不切断」的预期错位，叠加默认参数偏小。**

- 「按段落切」只决定**最小单元的提取方式**（怎么找边界），不决定**块是否完整**。
- 块是否被切断，取决于**单个段落/条款的 token 数 vs 该粒度预算（小块 150 / 大块 1200）**。超预算一律按 token 窗口硬切，与是否"按段落切"、是否有重叠无关。
- 重叠（overlap）只在**块与块的接缝处**回填尾部若干 token，缓解"边界词被腰斩"，**无法阻止一个超预算段落被切成多块**。

---

## 2. 当前切分流程（代码事实）

`services/chunker.py` 的 `chunk_document_dual` → `_merge_budgeted`：

```
1. _units_with_offsets(text, strategy)      # 按策略提取最小单元（默认 paragraph=段落/句末）
2. _count_tokens(units)                     # 批量 token 计数（chonkie，中文≈1字1token）
3. _merge_budgeted(units, max_tokens, overlap_tokens, granularity):
     for u in units:
         if u.tokens > unit_budget:         # ← 单元本身超预算
             _token_windows(u, unit_budget) # ← 按 token 窗口【硬切】成多块
             continue
         if 装得进当前缓冲: buf.append(u)    # 整单元入块
         else: 落库当前缓冲 + 尾部回填重叠 + 开新块
```

**关键路径**：当「单个段落的 token 数 > 块预算」时，走 `_token_windows` 硬切。小块预算 150 token ≈ 150 汉字，而公文段落（如"一、指导思想"整段、"（一）总体要求"整段）动辄 200–500 字，**几乎必然超预算 → 被切成 2–4 截**。这就是"完整性丢失"的直接来源。

---

## 3. 为什么重叠没解决问题

`_merge_budgeted` 的重叠是**尾部回填**：

```
上一块 [A B C D] ｜ 下一块 [C D E F]   ← 只在边界回填 C D 两个单元
```

它保证的是"接缝处的上下文衔接"，而不是"某个段落整体在一块里"。当段落被 token 窗口硬切时，切点由 `max_tokens - overlap` 步长决定，重叠只是让相邻两块多带一点彼此的开头/结尾，段落本身已被拆散。

---

## 4. 丢失完整性的三个具体成因

| 成因 | 机制 | 后果 |
|------|------|------|
| **① 小块预算偏小** | `small_max_tokens=150`，常见公文段落 200–500 字 | 单段被切成 2–4 个小块，检索召回时单块语义残缺 |
| **② 大块预算仍不够覆盖整节** | `large_max_tokens=1200`≈1200 字，公文一节/一章常 2000–5000 字 | 生成注入的大块仍不含完整条款，上下文不完整 |
| **③ 条件父块注入有限** | `parent_inject_max_count=2`、总预算 3000 token | 若某段内容散落在多个大块，注入可能覆盖不全 |

---

## 5. 解决方案（分三期，按投入从小到大）

### 5.1 短期：调配置（零代码，立即见效）

调大双粒度 token 预算，让常见段落/条款能整体落入单块：

| 参数 | 现值 | 建议值 | 理由 |
|------|------|--------|------|
| `small_max_tokens` | 150 | **300–400** | 覆盖多数自然段，避免段落硬切 |
| `small_overlap_tokens` | 20 | 30–50 | 增强接缝衔接 |
| `large_max_tokens` | 1200 | **2000–3000** | 更接近完整一节 |
| `large_overlap_tokens` | 100 | 150–200 | 大块接缝衔接 |
| `parent_inject_max_count` | 2 | 2–3 | 覆盖更多相邻大块 |

> 均在配置中心校验区间内（small 50–400，large 400–4000），改库即生效，无需重启、无需改代码。

### 5.2 中期：单元完整性保护（小改代码）

在 `_merge_budgeted` 增加**"段落/条款原子性"**：

- 当识别出条款标题（`_SECTION_RE`，如"一、""（一）""第一条"）时，把「标题 + 其下正文」作为**不可拆单元**（`chunker._section_units` 已实现该单元提取逻辑，需在双粒度路径启用并打通 token 计数）。
- 对未触发标题但单段 ≤ `max_tokens` 的段落，**绝不以 token 线切断**（现有逻辑已保证"单元超预算才切"；关键是让默认 small 足够大，使常见段落不超预算——即 5.1）。
- 仅当**单个条款本身**就 > 预算时，才退化为按段落（而非按裸 token 窗口）硬切，尽量在句子边界断。

### 5.3 长期：结构感知切分（与切分策略打通）

- 双粒度路径支持 `strategy=section`（现有 `chunk_document_dual` 已接收 strategy 入参，但入库默认走 `paragraph`）。
- 对公文文种，切分主策略改为「章节/条款优先」，段落作兜底——使"第X条/一、"级别整体入块，长条款再按段落细分。
- 收益：检索单元语义完整、生成注入上下文完整，且更贴合公文"按条款作答/引用"的真实场景。

---

## 6. 建议与决策点

1. **先执行 5.1 调参**（成本最低、立即缓解），用现有语料实测段落被切比例是否下降。
2. 若调参后仍有长条款被切 → 上 5.2（条款原子性）。
3. 中长期目标 → 5.3（section 策略进双粒度），与 `chunker` 已有的章节识别能力打通。

> 注意：块越大，单块 embedding 语义越"稀释"（小块利于精召、大块利于上下文），这是 small-to-large 模式的固有权衡。调大 small 时建议同步观察检索准确率（评测台），而非一味求大。

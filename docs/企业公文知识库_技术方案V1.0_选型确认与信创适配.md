## 2. 涉密定性确认：企业秘密（情形 B）

### 2.1 结论

你确认是**"仅内网企业秘密"**，即未定密的经营数据、人事信息、未公开方案等，不属于《保守国家秘密法》界定的国家秘密。

**这意味着：**

| 事项 | 情形 A（国家秘密） | **情形 B（企业秘密，你的情况）** |
|---|---|---|
| 承建方涉密资质 | 必需 | **不需要** |
| 分级保护测评 | 必需 | **不需要** |
| 运行环境 | 涉密信息系统（物理隔离） | **私有化内网即可** |
| 云端 API（涉密数据） | 绝对禁止 | **禁止**（数据合规要求，非法律强制） |
| 云端 API（脱敏样例） | 通常也禁止 | **可以用于开发验证** ✅ |
| 等保 | — | 视单位要求，一般二级/三级 |

《MVP 方案》第 0.1 节的阻塞项**就此解除**。

### 2.2 但仍有三条红线

等级降了不代表没有约束，以下三条必须落到工程上：

| # | 红线 | 落地措施 |
|---|---|---|
| R1 | 正式环境的真实公文不得出网 | 部署环境出口防火墙封禁公网；模型服务不配公网路由；**上线验收时做一次流量抓包验证** |
| R2 | 云端模型只能碰非真实数据 | 见 2.3 节硬约束设计，不依赖人的自觉 |
| R3 | 内网 ≠ 可以随便传 | 文件导出、外发须有水印与审计；导出行为全量留痕 |

### 2.3 "开发用云端、部署切本地"的硬约束设计

仅靠"上线前记得改配置"是不够的——这是典型的人为失误高发点。落地为三层防护：

```
第一层｜Provider 隔离
        LocalProvider（vLLM/内网）  ← 默认且 CSP 生产环境唯一可选
        RemoteProvider（云端 API）  ← 默认禁用，需显式环境变量开启

第二层｜启动自检
        应用启动时读取 ENV_PROFILE：
          若 = production 且检测到 RemoteProvider 启用 → 拒绝启动并报错
          若为 dev → 允许，但在每次启动时打印醒目风险提示

第三层｜出口拦截
        RemoteProvider 发出请求前做敏感词预检：
          命中关键词（单位名/项目代号/人名职务/惯用标识）→ 直接拒绝并记审计日志
        同时在部署环境通过网络策略封死出口，不做单点依赖
```

**第三层是关键**：它是唯一不依赖应用正确性的防线。即使前两层被误改，网络层面仍然封死。

### 2.4 云端 API Key 的使用纪律

开发期间的云端 API Key 不得提交进代码库；开发完成后 Key 作废；云端服务商的数据留存政策需确认（是否用于训练）。**建议专门确认所选云端服务的"数据不用于训练"条款。**

## 3. 信创要求带来的技术变更（本章最重要）

信创不是一个"最后装系统时换一下"的要求，它会反向约束前面所有的选型。以下是必须调整的点。

### 3.1 组件清单调整

| 组件 | 原选型 | 信创影响 | **建议调整** |
|---|---|---|---|
| 检索引擎 | Elasticsearch 8.x | **License 风险**：ES 7.11 起为 Elastic License / SSPL，非 OSI 认证开源协议，信创自主可控审查中常被质疑 | **改为 OpenSearch**（Apache 2.0，ES 7.10 fork），支持 kNN 向量检索 + IK 分词插件 |
| 对象存储 | 本地文件系统 / S3 兼容（抽象层） | AGPLv3，且近年社区版功能有裁剪趋势 | **MVP 先用本地文件系统 + 存储抽象层**，二期再评估国产对象存储 |
| 关系库 | PostgreSQL / MySQL | 需替换为目录内产品 | **达梦 / 人大金仓 / OceanBase**，按单位现有采购定 |
| 缓存队列 | Redis | Redis 7 起改 BSD/RSAL 双许可 | 视目录可用 Redis 兼容产品，或用关系库 + 任务表替代轻量队列 |
| 操作系统 | CentOS 系列 | 已停止维护 | **麒麟 / 统信 UOS / openEuler** |
| 应用运行时 | Python | 无影响 | 确认目标 OS 的 Python 版本与编译工具链可用 |
| **推理算力** | NVIDIA GPU | **核心冲突，见第 5 章** | **须先确认目录允许型号再采购** |

### 3.2 关于 ES → OpenSearch 的建议（需你拍板）

| | Elasticsearch 8.x | OpenSearch |
|---|---|---|
| 协议 | Elastic License 2.0 / SSPL | **Apache 2.0** |
| 向量检索 | 支持 kNN | 支持 kNN |
| 中文分词 | IK | IK 插件（社区维护） |
| RRF 融合 | 支持 | 支持 |
| 功能差异 | — | 基本对齐 ES 7.10，本项目用到的能力均覆盖 |
| **信创审查风险** | 中 | **低** |

**建议改 OpenSearch。** 迁移成本很低（本项目只用到基础检索能力），但能规避一个在验收阶段才爆出来的合规问题。如果你单位信创审查不卡协议，ES 也能用——**请你确认这一点**。

### 3.3 信创环境下的运行风险清单

| 风险 | 说明 | 应对 |
|---|---|---|
| 依赖包无国产 OS 版本 | 部分 Python 包无 ARM/国产版 wheel，需源码编译 | P1 阶段做**环境冒烟测试**，尽早暴露 |
| 无外网 PyPI | 内网环境通常不能访问公网 pip 源 | 需搭建**内网 PyPI 镜像**，或使用离线 wheel 包交付 |
| 字体缺失 | 方正小标宋、仿宋_GB2312 需授权采购 | 提前购置，P4 阶段前到位 |
| 推理算子不兼容 | 昇腾等国产卡的算子支持可能与 CUDA 有差异 | 见第 5 章，先验证后采购 |
| 模型权重获取 | 内网无法从 ModelScope 下载 | 需**离线下载后介质导入**，并确认模型许可允许内网部署 |

## 5. GPU 选型与采购建议（🔴 优先处理）

### 5.1 为什么现在不能下单

你同时给了两条信息：**"需要信创"** 和 **"GPU 待采购"**。这两条组合起来是一个典型的采购陷阱：

> 如果按常规选型买了 NVIDIA（RTX 4090 / A10 / L40S 等），很可能**不符合本单位的信创验收目录**，而 GPU 是高价值、难退货的资产。

**因此第一步不是选型号，而是拿到清单。**

### 5.2 采购前的四个前置动作

| 顺序 | 动作 | 负责方 | 产出 |
|---|---|---|---|
| 1 | 向信息化/采购部门索取 **信创合规 AI 加速卡清单** | 你方 | 可选型号列表 |
| 2 | 明确信创是"必须全栈国产"还是"可用非国产 + 备案说明" | 你方 | 约束等级 |
| 3 | **借/租一台目标型号做验证**（不要直接买） | 双方 | 跑通性验证报告 |
| 4 | 确定采购数量与到货时间 | 你方 | 采购计划 |

**第 3 步不能省。** 国产算力上跑 Qwen3 + vLLM + Embedding，可能遇到算子不支持、驱动版本不匹配、性能远低于标称等问题。**租一台测两周，成本远低于买错一批。**

### 5.3 验证清单（拿到机器后必须跑通的项）

```
□ 目标 OS（麒麟/UOS）能正常识别加速卡，驱动安装无报错
□ PyTorch / CANN 等基础框架可用，torch 能调用设备
□ 目标生成模型（如 Qwen3-14B/32B）能加载并完成一次推理
□ 量化方案（Int4/AWQ/GPTQ）在该硬件上可用
□ vLLM（或对应推理框架）能起服务，实测生成速度满足 <30s/1500字
□ Embedding 模型能跑，实测吞吐（chunks/s），据此推算 240 万切片入库耗时
□ Reranker 模型能跑，实测单次重排延迟（应 <100ms）
□ 并发压测：模拟 8 路并发生成，观察是否 OOM、延迟是否可接受
□ 长时间运行稳定性（≥24h）
```

**建议由我做一份完整的验证脚本**，你方拿到机器后直接跑，把结果贴给我即可定位问题。

### 5.4 候选参考（仅供核对，须以你们目录为准）

| 路径 | 候选 | 显存 | 可承载 |

| 非信创·经济 | RTX 4090 / RTX 6000 Ada | 24 / 48 GB | 32B Int4 或 14B BF16 + 小模型 |
| 非信创·推荐 | L40S / A6000 | 48 GB | 32B Int4 + Embedding + Rerank 共存较从容 |

### 5.5 我的推荐配置方向

在 20 并发、200 用户的规模下：

- **省事方案**：单张 ≥48GB 卡，生成 + Embedding + Rerank 共存，**批量入库任务安排在夜间错峰**
- **从容方案**：两张卡，卡 1 专做在线生成，卡 2 做 Embedding/Rerank 与批量任务
- **不要**：为这个规模上多机多卡推理集群，纯属浪费

## 6. 模型方案建议

### 6.1 生成模型

你提到"Qwen3 8B / 27B 量级"，这里需要明确一个点：**Qwen3 的实际可选规格需要以采购时 ModelScope 上可用为准**（各系列的规格会随版本调整）。就公文写作这个任务，我的建议：

| 场景 | 建议规格 | 理由 |
|---|---|---|
| 单卡 24GB | 14B 量化（Int4/AWQ） | 公文写作对逻辑深度要求中等，14B 已可产出合格稿件 |
| 单卡 ≥48GB | **32B 量化**（推荐） | 长文结构稳定性、公文语气、指令遵循明显优于小模型 |
| 双卡 / 80GB | 32B 非量化 | 效果上限最高，成本也最高 |

**对"报告""工作方案"这类长文，模型规格的差距会被放大**——小模型容易写到后半段结构松散、重复表述。所以如果预算允许，**建议向 32B 靠**。

**必须做的动作**：选定 1–2 个候选规格后，用你的**真实公文任务**做盲测对比，不要用排行榜下结论。

### 6.2 Embedding 模型

Qwen3-Embedding 系列是可以的。选型要点：

| 要点 | 说明 |
|---|---|
| 规模 | Embedding **一次性离线成本**，240 万切片虽耗时长但只做一次 → **可以用较大规格（4B/8B）** |
| 关键指标 | 中文语义、长文本支持（公文常有长段落）、是否支持稀疏向量（配合 BM25） |
| 验证 | 必须用真实样本做召回评测，见第 8 章 |

> 有一点要注意：**Embedding 模型一旦选定并建完索引，后续更换意味着全量重建**（240 万切片重跑数小时 + 索引重建）。所以选型阶段务必一次选对，宁可多花一周评测，也不要上线后再换。

### 6.3 Reranker —— 这里你可能会踩坑

你的答复是"rerank 也用 Qwen"，方向上没问题，但**规格要往下调**：

> **核心区别：Embedding 是离线成本，Rerank 是在线实时成本。**

Reranker 要对 top-30~50 的候选逐条打分，每次用户查询都要跑几十次推理。**如果用 8B 的 Reranker，延时很可能无法接受。**

| 建议 | 理由 |
|---|---|
| **选 ≤1B 的小规格 Reranker** | 单次延迟应控制在 50–100ms 内；重排的效果增益主要来自"是否做重排"，而非"重排模型有多大" |
| 若 Qwen3-Reranker 有小规格版本则优先用（与 Embedding 同源一致性好） | 否则备选 bge-reranker-v2-m3 等成熟中文方案 |
| **必须实测**：候选数量 50 时的端到端重排延迟 | 这是硬指标，不达标就砍候选数或降规格 |

**这条如果不注意，很可能出现"效果很好但每次查询要等 5 秒"的情况，直接毁掉用户体验。**

### 6.4 模型评测（强烈建议，不可省）

不要相信榜单。用你的真实数据做一次最小评测：

```
评测集：真实公文查询 100–200 条（由业务方提供"用户会怎么搜"）
答案：每条对应的相关文档 2–5 篇（人工标注）
方法：候选召回 Top50 → 重排 Top5 → 计算 Recall@5 / MRR@5
对比组：不同 Embedding / 不同 Reranker / 有无 BM25 融合
工具：我可提供现成评测脚本（见第 9 章）
```

半天到一天能跑完，但能避免"上线后发现检索不准，不知道是 Embedding 的问题还是切片的问题"。

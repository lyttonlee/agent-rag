## 0. 开篇：两个必须先解决的问题

在进入设计之前，有两处输入的冲突必须澄清。这两条不是"文档细节"，而是会决定项目能否上线的前置条件。

### 0.1 【阻塞项 A】涉密场景与云端模型互斥

| 你的输入 | 冲突 |
|---|---|
| 第 5 条：模型资源先云端 | ← 互斥 → |
| 第 7 条：合规要求涉及涉密信息 | |

**判断取决于"涉密"的确切含义，二者处理结果完全不同：**

| 情形 | 定义 | 云端模型是否可用 | 环境要求 |
|---|---|---|---|
| A. 国家秘密 | 《保守国家秘密法》界定的秘密/机密/绝密级 | **绝对不可用** | 涉密信息系统，需分保测评，承建方需涉密资质 |
| B. 企业商业秘密/内部敏感信息 | 未定密但不宜外传的经营数据、人事、未公开方案 | **原则上不可用** | 私有化内网即可，通常够用 |

**只有情形 A 才真正叫"涉密"，但两种情形的结论是一样的：本项目的生成、Embedding、重排全流程不得调用任何公网 API。**

附带一层容易忽略的点：**"完全私有化内网" ≠ "涉密网络"**。企业内网通常不具备处理国家秘密的资质，若确属情形 A，内网环境本身还需单独建设并通过测评。请确认属于哪种情形——这直接决定第 11 节的部署方案该怎么走。

**本方案采用的默认处理（供确认）：**

> **双轨制。** 云端模型仅用于在**脱敏样例数据**上做产品形态验证与技术预研，全程不接触真实业务数据；MVP 正式交付与试点一律使用**内网私有化模型**。二者通过模型抽象层切换，业务代码零改动（见 4.4 节）。

这样做的代价是需要提前采购/协调内网算力；收益是避免"云端跑得好、上线要重做"的返工。**若连云端验证也不允许（情形 A 常见），则直接全本地。**

### 0.2 【澄清项 B】"文种"被答成了"格式"

原文问的是"首批必须支持哪些**文种**"（通知、报告、请示……），收到的是 **docx / pdf / ofd / wps** —— 这是**文件格式**，不是文种。两个维度都需要，本方案按如下处理：

- **文件格式**（3.4 节）：按你的要求，导入支持 docx / docx-based wps / pdf（含 OFD 说明）；导出支持 docx / pdf / ofd，其中 OFD 有专门建议。
- **文种**：仍需你确认。**推荐首批 8 类**（见 3.3 节），在缺少你明确答复前，方案按此 8 类估算工作量。

## 1. MVP 目标

### 1.1 一句话定义

> 在**完全私有化的内网**中，用 **20 万篇公文积累的知识**，帮助 **200 名用户**把常见公文起草从"翻文件半天、落笔一小时"压缩到"选文种、填要素、十分钟出可送审初稿"，且**每一处事实都能点开原文核实**。

### 1.2 MVP 成功标准

| 维度 | 目标 | 判定方式 |
|---|---|---|
| 内容可用 | 生成的初稿，**人工修改量 ≤ 40%** 即可送审 | 试点部门 10 人 × 20 篇实测 |
| 事实可信 | 事实性错误率 ≤ 5%；每处引用可溯源 | 人工抽审 200 段 |
| 格式规范 | 导出 docx 符合 GB/T 9704-2012 核心项 | 逐项校验 50 篇 |
| 效率提升 | 单篇起草耗时降低 ≥ 50% | 试点前后对比 |
| 安全合规 | 无涉密数据出网；操作全审计 | 流量审计 + 日志核查 |

**MVP 不追求**：多功能、高并发、复杂流程。把一条主链路做到可用 > 十个功能做到半吊子。

## 2. 规模口径与容量测算

### 2.1 输入口径

| 项 | 数值 | 备注 |
|---|---|---|
| 注册用户 | 200 | 实际日活估算 60–100 |
| 并发用户 | 20 | 并发不等于同时生成，实际并发生成请求约 3–8 |
| 文档总量 | 200,000 篇 | 首期入库规模，后续年增约 15–30% |
| 集成要求 | 无 | 自建账号体系，无 SSO/OA 对接 |

### 2.2 由规模推导的架构结论

**这是本次方案最重要的一次修正：原 SRS 按 2000 用户/200 并发设计，采用的是微服务 + 高可用 + 分布式检索的思路；按实际规模，这套是过度设计。**

| 维度 | 原 SRS 假设 | 实际规模 | 结论 |
|---|---|---|---|
| 应用架构 | 微服务集群 | 20 并发 | **模块化单体**，进程数 ≤ 4 |
| 检索集群 | Milvus 集群 | 约 240 万向量 | **单节点**向量库足够，无需分片 |
| 高可用 | 99.9%、无单点 | 内部工具级 | 单机 + 备份即可，允许计划内停机 |
| 容器编排 | Kubernetes | 单实体 sustaining | **Docker Compose** 起步，K8s 是负担 |
| 协同编辑 | 多人实时协同 | MVP 无此需求 | **移除**，改用版本管理 + 单人编辑锁 |

**做减法的收益**：交付周期可压缩 30–40%，运维成本大幅下降，团队精力集中到真正决定成败的地方——**知识库质量**。

### 2.3 容量详细测算

**切片量估算**

| 参数 | 取值 | 说明 |
|---|---|---|
| 篇数 | 200,000 | — |
| 平均每篇字数 | 3,500 字 | 公文普遍偏短，含简要类文件 |
| 切片大小 | 400 字（overlap 80 字） | 见 5.2 节依据 |
| **切片总数** | **约 218 万** | 保守取 **240 万**进行容量规划 |

**存储测算**

| 项目 | 计算 | 容量 |
|---|---|---|
| 原文文件 | 20 万 × 平均 500 KB | 100 GB |
| 向量数据 | 240 万 × 1024 维 × 4 B | 9.8 GB |
| 向量索引开销 | HNSW 约 +40% | 4 GB |
| 全文倒排索引 | ES 索引约原文的 1.2 倍 | 12 GB |
| 业务数据 + 日志 | 用户、版本、审计 | 10 GB |
| **合计** | | **约 136 GB** |
| **建议配置** | 含年增 30%、处理临时文件 | **≥ 512 GB NVMe SSD** |

**解析与向量化耗时测算**

| 阶段 | 单篇耗时 | 总量 | 优化后 |
|---|---|---|---|
| 文本型 PDF/DOCX 解析 | 0.5–2 s | 单线程 55–110 小时 | 8 进程并行 → **7–14 小时** |
| 切片 | < 0.1 s | 可忽略 | — |
| Embedding（单卡 4090/A10，约 200 chunks/s） | — | 240 万 chunks → 3.3 小时 | **按 8 小时窗口规划** |
| ES 索引写入 | 批量写入 | — | 约 4 小时 |

> ⚠️ **最大不确定性：扫描件 PDF 占比。** 若历史公文存在大量扫描件，需走 OCR，单页 1–3 秒——按 20 万篇 × 8 页估算，OCR 需**数百小时**，且错误率上升。**强烈建议在动工前做一次样本抽样**（随机抽 200 篇，统计扫描件占比、平均页数、是否有文字层），这个数字会直接影响工期和硬件投入。这是本项目目前最大的工期风险点。

### 3.4 文件格式支持

**导入 / 解析**

| 格式 | 支持方式 | 备注 |
|---|---|---|
| .docx | 原生（python-docx） | 主格式，解析质量最好 |
| .wps | 调用 WPS 转换组件 → docx → 解析 | 见下方说明 |
| .pdf（文字层） | 原生（PyMuPDF / pdfplumber） | 需保留标题层级 |
| .pdf（扫描件） | OCR（PaddleOCR） | **取决于扫描件占比，见 2.3 节警告** |
| .ofd | 读取（ofdrw） | MVP 支持读取，导出延后 |
| .doc（旧版） | 转换中间件 → docx | 视存量占比决定优先级 |

> **WPS 格式处理**：.wps 为私有格式，常规做法是依赖 WPS 二次开发接口做转换为 docx。内网无外网激活时需确认 WPS 授权形态。**务实建议**：MVP 阶段在导入环节提示"请另存为 .docx"，同时后台尝试自动转换；若存量 .wps 极少，此项可完全跳过。

**导出**

| 格式 | 实现方式 | MVP |
|---|---|---|
| .docx | docxtpl / python-docx 模板渲染 | ✅ 必须 |
| .pdf | LibreOffice headless 转 PDF | ✅ 必须 |
| .ofd | 见 3.5 节 | ⏸ 建议二期 |

### 3.5 关于 OFD 的建议

OFD（GB/T 33190）是党政机关电子公文的版式标准，你们把它列进来说明有正式电子公文流转/归档诉求。**但从工程角度，我建议 OFD 放二期，理由如下：**

| 因素 | 说明 |
|---|---|
| 生成复杂度 | OFD 不是简单转换，需构建版式描述；成熟开源方案主要是 Java 侧的 ofdrw，Python 生态薄弱 |
| 技术栈耦合 | 若整体用 Python，接入 ofdrw 需跨语言服务，对 20 并发的项目性价比低 |
| 实际用法 | 常见链路是 docx 起草编辑 → PDF 审阅流转 → **归档环节**由专业版式系统统一转 OFD |
| 替代方案 | MVP 提供 docx + pdf 已覆盖 90% 使用场景；确需 OFD 时可接第三方转换服务或放到 V2 |

**若 OFD 属于必须项，则需反过来影响技术选型（后端选 Java）——请在选型时明确。** 这是一个会反向决定架构的需求点。

## 4. 总体架构设计

### 4.1 架构原则

1. **轻量为先**——组件数最小化，能一个进程跑完的不拆两个
2. **检索质量优先**——资源向知识库倾斜，这是唯一决定成败的地方
3. **可替换**——模型、向量库、解析器通过接口抽象隔离
4. **可降级**——模型服务异常时，检索与模板能力仍可用

### 4.2 逻辑架构

```
┌──────────────────────────────────────────────────────┐
│  接入层   Web 端（响应式）· 反向代理 · 内网访问控制        │
├──────────────────────────────────────────────────────┤
│  应用层   账号权限 │ 文档管理 │ 写作会话 │ 审查 │ 流程    │
│          （模块化单体，Python FastAPI）                │
├──────────────────────────────────────────────────────┤
│  AI 编排层  Query改写 → 混合检索 → 重排 → 上下文组装      │
│            → 生成 → 引用注入 → 后置校验                 │
├──────────────────────────────────────────────────────┤
│  模型层    LLM │ Embedding │ Reranker（内网私有化部署）   │
├──────────────────────────────────────────────────────┤
│  数据层    ES + 向量库 │ 关系库 │ 对象存储 │ 缓存/队列    │
├──────────────────────────────────────────────────────┤
│  支撑      审计日志 │ 监控 │ 备份 │ 离线任务队列          │
└──────────────────────────────────────────────────────┘
```

### 4.3 MVP 建议部署拓扑

单台服务器即可承载全部角色，是最省事也够用的方案：

```
应用服务器 × 1（或 2，应用/AI 分离）
  ├─ 应用服务进程
  ├─ AI 服务进程
  ├─ 向量库 / ES
  ├─ 关系库
  └─ 对象存储
推理服务器 × 1（或与应用共用）
  └─ vLLM / Xinference：LLM + Embedding + Reranker
```

**若 GPU 服务器与应用共用一台**，需错峰运行批量入库任务（放在夜间），避免影响在线生成响应。MVP 期推荐共用，二期再拆。

### 4.4 模型抽象层（应对"云端/本地切换"的关键设计）

```
业务代码  →  ModelProvider 接口  →  LocalProvider（vLLM，内网）
                                →  RemoteProvider（云端 API，仅验证期）
```

- 业务层只依赖 `ModelProvider`，通过配置项切换实现，代码零改动
- **RemoteProvider 默认禁用**，开启需显式配置 + 启动时强提示 + 审计日志标记
- 增加一道保险：`RemoteProvider` 的数据出口做**敏感内容拦截**，检测到疑似涉密/敏感关键字直接拒绝发送

这道设计让"先云端验证、后切换本地"成为低成本的配置切换，而不是二次开发。

## 5. 核心设计：知识入库流水线

**这是 MVP 中工程量最大的部分，也是最决定最终效果的部分。建议投入整体工时的 35–40%。**

### 5.1 流水线阶段

```
① 采集导入  → ② 去重  → ③ 格式归一  → ④ 解析提取
   → ⑤ 清洗  → ⑥ 元数据抽取 → ⑦ 切片 → ⑧ 向量化 → ⑨ 入库 → ⑩ 质检
```

| 阶段 | 关键处理 | 陷阱 |
|---|---|---|
| ① 采集 | 目录扫描 / 批量上传，记录来源路径 | 公文系统导出的目录结构往往不规范 |
| ② 去重 | 文件 MD5 + 正文 SimHash | 同一文件多版本、转发件重复，不处理会污染召回 |
| ③ 格式归一 | 非标准格式转 PDF/docx | .wps / .doc 需转换中间件 |
| ④ 解析 | 保留标题层级、表格、落款 | **扫描件是最大变量，见 2.3** |
| ⑤ 清洗 | 去页眉页脚水印、合并断行、修正常见 OCR 错字 | 公文页眉多为固定标语，不清理会大量误召回 |
| ⑥ 元数据抽取 | 发文机关、文号、成文日期、文种、密级、责任部门 | 规则优先 + 模型兜底（见下） |
| ⑦ 切片 | 按标题层级 + 语义（见 5.2） | — |
| ⑧ 向量化 | bge 系列，批推理 | 需错峰、支持断点续跑 |
| ⑨ 入库 | ES + 向量库双写，权限标签随行 | 权限字段必须在入库时写入，不可后置过滤 |
| ⑩ 质检 | 随机抽检 100 篇，人工评估解析正确率 | **必须做**，否则错误静默扩散 |

**元数据抽取策略**：优先用正则/规则提取（文号、日期、机关名有固定模式，准确率更高且零成本），规则失败时才调用模型兜底。不要一上来就用大模型抽取——20 万篇的成本和耗时都不划算，且规则的可控性更好。

### 5.2 切片策略（中文公文专项）

公文的强结构性是优势也是难点，通用切片策略效果普遍不佳。推荐：

| 要点 | 做法 | 理由 |
|---|---|---|
| 切分单位 | **优先按标题层级**（一、/（一）/ 1. /（1）），层级过长时按 semantic 二次切分 | 公文段落边界清晰，标题是最好的语义边界 |
| 目标大小 | 300–500 字，overlap 80 字 | 太小丢失论证完整性，太大稀释相关性 |
| **上下文前缀** | 每个切片前置拼接「文档标题 ｜ 发文机关 ｜ 成文日期 ｜ 所在标题路径」 | **这是提升中文公文检索质量最有效的一招**，解决切片脱离文档后语义不完整的问题 |
| 表格处理 | 表格整体独立成片，附表格标题 Markdown 化 | 表格跨切会被截断成废内容 |
| 特殊区块 | 抄送机关、附件说明等不参与语义召回，仅作元数据 | 减少噪声召回 |
| 禁止跨团 | 不跨越"发文机关署名/成文日期"边界合并 | 避免把落款混进正文 |

> **上下文前缀示例**：
> `【XX公司关于2025年度安全生产工作的通知 ｜ XX公司办公室 ｜ 2025-03-12 ｜ 三、工作要求 > （二）隐患排查】` + 正文切片
>
> 这个前缀同时用于 Embedding 输入和 BM25 索引，能显著改善"这份是哪年的文件""哪个部门发的"这类约束性查询。

### 5.3 任务工程要求

20 万篇的处理量，必须有工程保障：

- **Celery + Redis** 任务队列，支持分片并行（8–16 worker）
- **断点续跑**：记录每个文档的完成阶段，失败只重试该文档
- **幂等**：重复执行同一文档不产生重复索引
- **进度看板**：总进度、失败清单、平均耗时，失败原因分类
- **失败隔离**：单篇解析失败不影响整体批次，进入待处理队列
- **可重跑**：切片策略/模型更换时能一键全量重建，且不影响在线检索（影子索引 + 切换）

## 6. 核心设计：检索与生成

### 6.1 检索链路

```
用户 Query
  ↓
① 权限解析 → 得到可见范围过滤器（密级 + 部门 + 知识库授权）
  ↓
② Query 改写/扩展（可选，LLM 生成 2–3 个变体）
  ↓
③ 并行双路召回
   ├─ BM25（ES + IK 分词，中文必需）  Top 50
   └─ 向量召回                        Top 50
  ↓
④ 元数据过滤（文种 / 年份 / 效力状态）
  ↓
⑤ RRF 融合去重  → Top 30
  ↓
⑥ Rerank（bge-reranker）→ Top 5–8
  ↓
⑦ 上下文组装（去重、按相关度排序、截断控制）
  ↓
⑧ 送入 LLM，带引用标记生成
```

> **BM25 在公文场景不可替代。** 文号（`XX〔2025〕15号`）、专有名词、精确数字、机构全称这类查询，向量检索表现很差而关键词检索精准。**混合检索不是优化项，是必需项。**
>
> **中文分词必须配置 IK 分词器**（或同类），并维护**自定义词典**——把单位名称、部门全称、常用公文术语、项目代号加入词典，这一步对召回质量提升非常明显，且成本低。

### 6.2 权限过滤设计

```
① 用户登录 → 解析角色/部门/密级
② 生成 filter 表达式，在检索请求层面下推：
   - ES: bool filter（security_level <= user_level AND dept IN visible_depts）
   - 向量库: 同表达式 / pre-filter
③ 组装上下文前再做一次二次校验（双保险）
```

**原则：权限过滤必须在检索阶段生效，而不是生成后过滤。** 后者等于已经把涉密内容喂给了模型，只是不显示给用户而已——在攻防视角下这是失效的控制。

### 6.3 生成与引用溯源

**Prompt 约束要点**

| 约束 | 内容 |
|---|---|
| 角色设定 | 资深公文起草人员，熟悉机关公文规范 |
| 依据限定 | **只能使用提供的检索材料中的事实**；未包含的信息不得编造 |
| 缺口处理 | 缺少材料时，输出占位符并标注 `【待补充：XXX】`，禁止自行填充数据 |
| 引用要求 | 每个事实性陈述后标注 `[序号]`，与材料清单对应 |
| 格式要求 | 按文种规范输出层级标题与固定表述 |
| 禁止项 | 不生成具体未经确认的数据、日期、人名职务 |

**引用溯源实现**

1. 生成时为每个材料分配编号，要求模型以 `[n]` 标注
2. 后处理：解析正文中的引用标记，建立「引用 → 材料 → 源文件 → 切片」映射落库
3. 前端：角标悬浮显示摘要，点击跳转原文并高亮定位切片
4. 来源卡片展示：文件名、发文机关、文号、成文日期、密级、**效力状态**
5. 废止文件被引用时显著告警

**后置一致性校验（重要）**

> 用正则抽取出生成文本中的**数字、日期、文号、机构名称**，与对应引用原文做字符串比对，不一致则标红告警。

这一步是防止"模型读了材料但仍写错数字"的最后一道防线。中文公文对数字准确性零容忍，这个校验的投入产出比很高。

### 6.4 无依据内容的处理

当检索结果为空或相关度过低时：

```
系统提示：「知识库中未检索到相关依据，以下内容基于通用公文范式生成，
          其中的数据、日期、文件名均需人工核实。」
并在导出文件时保留风险标识，提醒核稿人重点把关。
```

**绝不静默生成未经支撑的内容。** 这是信任的基础——宁可让用户知道"这块没依据"，也不能给出看起来很像真的假内容。

## 7. 核心设计：模板、格式与审查

### 7.1 模板体系

```
文种 → 模板（1:N）→ 要素字段定义 → 写作提示 → 正文骨架 → 样式配置
```

| 要素示例（通知） | 字段类型 |
|---|---|
| 标题事由 | 文本 |
| 主送机关 | 选择（来自组织库）/ 手填 |
| 发文依据 | 文本 + 素材插入 |
| 主要内容 | 富文本 / AI 生成 |
| 时间地点 | 日期 / 文本 |
| 落款机关 | 选择 |
| 成文日期 | 日期（默认今日） |

模板以 **docx 模板 + 占位符**形式维护（docxtpl），业务人员用 Word 就能改，不需要开发介入——这一点很重要，否则模板维护会长期卡在技术上。

### 7.2 国标合规要点（GB/T 9704-2012）

| 项目 | 要求 |
|---|---|
| 版头 | 发文机关标志、发文字号、签发人（上行文）、分隔线 |
| 标题 | 二号小标宋体，可分一行或多行，回行词意完整 |
| 主送机关 | 三号仿宋，顶格，后标全角冒号 |
| 正文 | 三号仿宋，首行缩进 2 字；层级：一、/（一）/ 1. /（1） |
| 附件说明 | 正文下空一行，"附件："+ 序号 + 名称 |
| 落款 | 发文机关署名、成文日期（阿拉伯数字）、印章位置 |
| 页面 | 页边距上 37mm、下 35mm、左 28mm、右 26mm；每页 22 行、每行 28 字 |
| 抄送/印发 | 版记部分规范排布 |

**实现建议**：字体落地依赖环境安装对应字库（方正小标宋、仿宋_GB2312 等），内网环境需提前安装——这是个容易在验收前才发现的小坑，建议在 M1 阶段就验证。

### 7.3 审查校对（规则驱动为主）

MVP 采用**规则引擎 + 词库**，不依赖模型——规则可控、成本低、响应快，且错误可解释。

| 检查项 | 实现方式 | 数据来源 |
|---|---|---|
| 要素缺失 | 模板必填项校验 | 模板定义 |
| 层级编号 | 正则检测跨级/跳级 | 规则 |
| 错别字 | 混淆词库（部署/布署、按排/安排） | 中文纠错词库 |
| 标点用法 | GB/T 15834 规则集 | 规则 |
| 数字用法 | GB/T 15835 规则集 | 规则 |
| 敏感/禁用词 | 分级词库（阻断/告警/建议） | 可维护词表 |
| 称谓与排序 | 机构排序库 | 组织信息 |
| 政治表述 | 表述规范库 | 业务方提供，需持续维护 |
| 引用一致性 | 6.3 节后置校验 | 引用映射 |

> **政治表述与敏感词库需要业务方（办公室/秘书处）提供初始版本并持续维护**，这不是技术能自建的内容。请把它列为业务方的交付义务之一。

## 9. 技术选型——待你确认

> 以下每项给出候选与我方推荐理由，请你拍板。**推荐方案已按"200 用户 / 20 并发 / 20 万文档"的最优性价比给出，而非最"先进"的方案。**

### 9.1 应用后端

| 方案 | 优点 | 缺点 | 适用 |
|---|---|---|---|
| **Python FastAPI（推荐）** | AI 链路同语言，无跨语言开销；生态最全；开发快 | 团队若不熟 Python 需适应 | 团队偏 AI/快速交付 |
| Java Spring Boot | 企业运维体系成熟；信创生态好；对接 ofdrw 方便 | 需额外维护 Python AI 服务，双栈成本 | 已有强 Java 团队 + OFD 必须 + 深度信创 |
| Go + Python | 性能高 | 双栈，200 并发无必要 | 不推荐 |

**推荐：Python FastAPI 模块化单体。** 规模决定了没必要为微服务付出代价。若 OFD 为硬需求 + 团队是 Java，则改选 Java。

### 9.2 检索与向量

| 方案 | 组件数 | 240 万向量 | 推荐度 |
|---|---|---|---|
| **ES 8.x（BM25 + dense_vector kNN + RRF）** | 1 | 够 | ★★★★ 组件最少 |
| ES（BM25）+ Qdrant（向量） | 2 | 够 | ★★★★ 检索质量略优 |
| ES + pgvector | 2 | 够 | ★★★ 依赖现有 PG |
| ES + Milvus | 2 | 过剩 | ★★ 运维成本高 |

**推荐：MVP 期 ES 单引擎起步**（若混合检索效果不达标，二期加 Qdrant）。理由：组件越少，出问题越好排查；这个规模远未到 Milvus 才有价值的量级。

### 9.3 AI 编排

| 方案 | 优点 | 缺点 |
|---|---|---|
| **自研编排 + LlamaIndex 组件（推荐）** | 完全可控，适配公文的引用/校验等定制需求 | 需投入编码 |
| RAGFlow | 开箱即用，中文文档解析强 | 定制化受限，深度改造成本上升 |
| Dify | 编排成熟，上手快 | 偏通用 Agent 平台，公文定制需绕 |
| 纯 LangChain | 灵活 | 抽象重，调试复杂 |

**推荐：自研轻量编排。** 理由是本项目的核心差异在"公文专项逻辑"（引用校验、文种结构化、国标合规），这些在通用平台上都是要绕开它的默认行为去做，长期看自研更省。

### 9.4 文档解析

| 方案 | 适用 |
|---|---|
| **python-docx + PyMuPDF（推荐 MVP）** | 结构化好、速度快、零依赖；适合文字层文档 |
| MinerU / Docling | 复杂版式、表格多时可评估，但重、慢 |
| PaddleOCR | 扫描件必需（取决于抽样结果） |

**推荐：MVP 用轻量库，扫描件按抽样结果决定是否引入 OCR。**

# 检索优化方案 V1.0

> 背景：用户反馈「很多问题无法检索，成功率低」，要求**至少具备 query 改写能力（检索不到时改写后重检）**，并明确这是后续重点优化方向。
> 本文为方案评审稿：先度量、再动手；每阶段有明确验收标准。配套落地配置见《企业公文知识库_接口文档》与配置中心（category=`retrieval` / `prompt`）。
> 代码基线：`backend/app/services/retrieval.py`（hybrid_retrieve）、`agent/policies.py`（is_no_useful_info）、`chunker.py`、`generation_prompt.py`。

---

## 一、现状链路与诊断

### 1.1 当前链路（代码事实）

```
用户 query
  → Qwen3-Embedding-4B 向量化（无 instruction 前缀）
  → 双路召回（各 top-50）：
      向量路  pgvector HNSW 余弦距离
      关键词路 zhparser 分词 + ts_rank_cd（plainto_tsquery）
  → RRF 融合（k=60）→ 取 top-8
  → Qwen3-Reranker-0.6B 重排（仅排序，不过滤；失败回退 RRF 序）
  → 密级/权限 WHERE 下推
  → 「无有用信息」双信号判定：top1 向量距离 > 0.60 且 关键词命中 = 0
```

### 1.2 失败模式分类（按对成功率的影响排序）

| # | 失败模式 | 根因（代码层） | 用户侧表现 |
|---|---|---|---|
| F1 | **词汇鸿沟**：口语化/简写提问 vs 公文书面语（"值班表" vs "汛期值班安排"；"三重一大" 被切碎） | query 原样进 embedding 与分词，无改写/扩展；关键词路 `plainto_tsquery` 无同义词 | 双路都召回不到 → 直接判定"无有用信息" |
| F2 | **边缘结果放行后答非所问**：距离 0.55、关键词 1 命中的弱相关材料进入提示词 | is_no_useful_info 要求"双信号同时异常"才拒；rerank 分只排序不设阈值 | 模型答"依据不足"或泛化而谈 → 用户感知"没检索到" |
| F3 | **复杂问题单路直检**："对比 A 制度和 B 制度的要求" 用整句做双路召回 | 无子问题拆解；RRF 融合被长 query 稀释 | 只命中其中一篇 |
| F4 | **切片粒度粗糙**：91 切片/34 篇（均值 2.7），paragraph 策略下长文切片仍可能主题混杂；800 字切片对短查询信噪比低 | chunk_size 默认 800、无父子切片/篇章标题加权 | 命中文档但 snippet 不覆盖问题点 |
| F5 | **参数不可调**：top_n=8、阈值 0.60、rerank 开关全部硬编码在 settings/env | 配置中心只有敏感词/适配器/模型 Profile 三类 | 无法按部署方语料快速调优 |
| F6 | **语料规模**：当前 34 篇种子库，覆盖率本身有限 | — | 合理拒答被感知为"检索差" |

> 结论：F1/F3 由**查询改写**解决（本方案核心）；F2 由**相关度阈值配置化**解决（衔接配置中心化任务）；F4/F5 是结构化调优；F6 靠接入放量，非算法问题。

## 二、度量先行（P0，不做这一步后续全是盲调）

没有通过率基线，就无法证明任何改动有效。建设轻量评测台：

- **评测集**：从 34 篇种子文档构造 30–50 条 (问题, 应中文档ID) 对，覆盖三类：
  - 直接事实型（文号、日期、数值）——考关键词路；
  - 语义泛型（"安全生产有什么要求"）——考向量路；
  - 词汇鸿沟型（口语提问，文档用书面语）——考改写。
  存放 `tools/eval/retrieval_eval.jsonl`，可手工扩充。
- **指标**（`tools/eval_retrieval.py` 输出）：
  - `recall@8`：应中文档进入 top8 的比例（检索成功率主指标）；
  - `no_result_rate`：触发"无有用信息"判定的比例；
  - `救回率`（改写上线后）：首次检索失败 → 改写后 recall@8 的比例（改写机制专属 KPI）；
  - `p95 延迟`：改写引入的额外耗时预算（硬约束，见下）。
- **基线**：先跑当前链路存档数字，作为 P1/P2 对比基准。

## 三、Query 改写机制设计（核心，用户最低要求）

### 3.1 触发条件（三重，任一命中即改写）

在 `hybrid_retrieve` 返回后、进入生成前判断：

1. `citations` 为空（空间无文档或全被过滤）；
2. `is_no_useful_info(resp)` 为真（双信号异常，现有逻辑复用）；
3. **rerank top1 分数 < 阈值**（新信号，F2 的对策）——分数阈值入配置中心
   （`retrieval.rerank_min_score`，默认建议 0.35，P1 用评测台标定；
   Qwen3-Reranker 输出经 sigmoid 归一化时 0.3–0.5 是常见弱相关带，需实测标定）。

> 防抖：同一 conversation 内相同 query 不重复改写（结果缓存，复用已有 Redis 可选组件或进程内 LRU）。

### 3.2 改写策略（LLM 实现，复用现有 ModelProvider，零新依赖）

| 策略 | 做法 | 适用 |
|---|---|---|
| **S1 术语规范化 + 同义扩展** | LLM 把口语 query 改写为"公文术语主干 + 2–3 个同义词"，如「值班表怎么排」→「值班安排 带班 值守 排班」 | F1 主力，几乎所有失败 query 先过 S1 |
| **S2 HyDE** | LLM 先生成一段"假设性答案/文档片段"（含公文术语），用其 embedding 做向量召回 | F1 语义路主力；对"概念型"问题提升显著 |
| **S3 子问题拆解** | LLM 把复杂 query 拆为 2–4 个可独立检索的子查询，分别召回后 RRF 合并去重 | F3；与 Agent 的 complex_task 计划天然衔接 |
| **S4 Step-back 抽象** | LLM 把具体问题抽象为上位概念再检索（"2025 年汛期值班" → "汛期 应急 值守制度"） | 细节查询失败时的补充轮 |

默认组合：**第一轮 S1+S2 并行**（两条改写 query 各检一次，结果 RRF 合并）；**第二轮 S3**（仅当第一轮仍失败且 query 较长/含并列结构）；S4 预留配置开关。轮次上限默认 2（`retrieval.rewrite_max_rounds`）。

### 3.3 合并与去重

- 各轮结果按 `chunk_id` 去重，RRF 分数取 max（不叠加，防原始 query 的高排位被稀释）；
- 改写轮的结果参与最终 rerank（rerank 输入 = 合并去重后的 top-8）；
- 最终 citations 标注 `rewritten: true` 与所用策略，进审计与前端"重试痕迹"展示（透明度）。

### 3.4 降级与防退化（红线）

- **改写 LLM 调用失败/超时**（默认 8s）：跳过改写，按原链路结果走——绝不让改写成为新故障点；
- **改写后仍无有用信息**：保持现有行为（direct_qa 委婉拒答 / 任务型自身能力 + 甄别声明），**不得**放松阈值放行弱材料——不编造是硬约束；
- **总延迟预算**：改写全程（含 LLM 改写 + 二次检索）p95 ≤ 6s；超预算自动截断后续轮次；
- **能力域**：改写复用 gen 模型，第三方客户端的 chat 域权限已覆盖，无需新权限。

### 3.5 可观测

- 审计日志新增 `action=query_rewrite`：原始 query / 策略 / 是否救回 / 各轮分数；
- 评测台 `救回率` 指标持续跟踪；
- 配置中心可一键关闭改写（`retrieval.rewrite_enabled`），故障时秒级回退。

## 四、其他优化杠杆（按性价比排序，均需评测台验证）

| 阶段 | 杠杆 | 预期 | 风险 |
|---|---|---|---|
| P1 | **Qwen3-Embedding query instruction**：query 侧加检索指令前缀（"为这个句子生成表示以用于检索相关文章："）后再 embed | 向量路信噪比提升，对 F1 直接有效 | 需 A/B：可能对短 query 反而扰；embedding 模型须支持 instruction（Qwen3-Embedding 支持，用评测台验证） |
| P1 | **rerank 分数阈值 + 相关度配置化**（3.1 第 3 条 + 配置中心化） | F2 对治；运维可调 | 阈值误杀 → 保守默认 + 双信号保留 |
| P2 | **切分调优**：按文种默认策略（制度类 section / 通知类 paragraph）；父子切片（先召回子切片、返回时扩展父级上下文） | F4 对治；snippet 覆盖问题点 | 需重建索引（提供重建工具，存量 91 切片重跑成本极低，20 万全量约 2.7h embedding） |
| P2 | **同义词/别名词典**（配置中心 `dict_custom` 类目落地）：关键词路查询扩展 | F1 对治，与 S1 互补（词典兜底 LLM 改写不可用时） | 词典维护成本；先仅 8 文种高频术语 |
| P3 | 章节标题加权（title 字段进 search_vec 权重）、多权重 RRF（按 query 长度动态调 keyword/vector 权重） | 边际提升 | 复杂度上升，非必要不做 |

## 五、分阶段路线图与验收标准

### P0 度量基线与评测台（0.5 天）
- 交付：`tools/eval/retrieval_eval.jsonl`（30+ 条）+ `tools/eval_retrieval.py`；
- 验收：输出当前链路 recall@8 / no_result_rate / p95 延迟基线数字。

### P1 查询改写 + 阈值配置化（1.5 天）★用户最低要求
- 交付：`services/query_rewrite.py`（S1/S2/S3 策略 + 合并去重 + 降级）；触发逻辑接入 `chat.py` / `generation.py` 双链路；`retrieval.*` 与 `prompt.*` 全量入配置中心；
- 验收：评测台 `recall@8` 相对基线 **+15% 以上**；`救回率 ≥ 40%`（首次失败 query 中）；p95 延迟增加 ≤ 3s；关闭开关后行为与基线一致（回归）。

### P2 切分与召回增强（1 天）
- 交付：按文种默认切分策略；父子切片（如采用）；同义词词典类目；
- 验收：recall@8 再 +10%；索引重建工具验证通过（重跑 34 篇无损）。

### P3 高级项（按评测数据决定是否做）
- 验收：任一杠杆带来 ≥ +5% recall@8 才合并，否则弃用（防过度工程）。

## 七、风险与约束

1. **不编造红线**：一切改写与阈值放宽不得让"无材料"问题拿到弱材料后硬答；拒答与甄别声明逻辑保持不变。
2. **延迟预算**：改写只在前置判定失败后触发（绝大多数正常 query 零额外开销）。
3. **隐私/出网**：改写用同一 gen 模型（内网/std），无新增外呼。
4. **存量索引**：P2 若改切分需重建索引，必须提供重建工具并先在 34 篇验证，再放量。
5. **不过度工程**：P3 每项先过评测台门槛（+5% recall@8）再进主干。

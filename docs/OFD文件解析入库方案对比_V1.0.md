# OFD 文件解析入库方案对比（V1.0）

> 背景：公文绝大多数为 OFD 格式（国标 GB/T 33190《电子文件存储与交换格式版式文档》）。
> 当前解析器仅支持 PDF / DOCX / TXT，OFD 直接抛「暂不支持的解析格式」。
> 本文给出多套方案对比，供决策选型。

---

## 1. 先弄清 OFD 是什么

| 特性 | 说明 |
|------|------|
| 本质 | **ZIP 容器**（文件头 `PK\x03\x04`）+ 内部 XML 结构 + 资源（字体/印章/图片） |
| 版式 | 固定版式文档，类似 PDF，但用 XML 描述版式与内容 |
| 核心文件 | `OFD.xml`（入口）、`Document.xml`（文档）、`Page_*.xml`（页面/版面） |
| 文字层 | 电子版 OFD **含文字层**（`TextObject`），可无损提取；少数签章/图片页无文字层需 OCR（与 PDF 扫描件同理，样本实测 96.7% 有文字层） |

**关键陷阱**：OFD 与 DOCX 都是 `PK` 魔数的 ZIP 包。当前 `parser.py` 的 `_sniff_format` 只要看到 `PK\x03\x04` 就判定为 `docx`，再用 `python-docx` 打开 OFD 会**静默解析失败或内容错乱**。因此 OFD 识别**不能只看魔数**，需要解包看根 XML 命名空间（`http://www.ofdspec.org/2016`）才能可靠区分。

---

## 2. 方案对比

### 方案 A：纯自研轻量解析（标准库 zipfile + ElementTree）

直接用 Python 标准库解 OFD 包，遍历 `Text_*.xml` 提取 `TextCode`/文字内容，按页面/段落重组文本。

| 维度 | 评价 |
|------|------|
| 文字提取 | ✅ 电子版 OFD 文字层无损提取，准确率高 |
| 结构保留 | ✅ 能拿到页面/段落顺序，可对接现有公文结构识别（条款/章节） |
| 依赖 | ✅ **零三方依赖**（纯标准库），内网离线可用，无授权风险 |
| 维护 | 需自维护命名空间映射、容错（不同厂商 OFD 略有差异） |
| 信创/国产化 | ✅ 完全自主可控，无二进制外部进程 |
| 版式还原 | ❌ 不做版式渲染（我们只需文本入库，不还原式样） |
| 工作量 | 中等（约 1 个解析模块） |

**适配点**：与现有 `parser.py` 的 `ParsedDoc(text, pages, is_scanned, scanned_pages)` 输出契约一致，改动最小。

### 方案 B：第三方 OFD 库（ofdrw / ofdbox）

用成熟开源 OFD 读写库解析。

| 维度 | 评价 |
|------|------|
| 文字提取 | ✅ 库已封装版式/文字解析 |
| 依赖 | ⚠️ 引入三方 Python 包；需确认内网 PyPI 可用（项目已配清华镜像，多数可拉） |
| 维护 | ✅ 库维护解析细节，我们少写容错 |
| 信创/合规 | ⚠️ 需确认所选库许可证（ofdrw 为 Apache-2.0，可商用） |
| 风险 | 部分库面向「生成 OFD」而非「读取」，读取 API 完整度需实测验证 |
| 工作量 | 小（API 对接），但要先验证读取能力 |

### 方案 C：OFD → PDF/DOCX 转换器（复用现有解析）

用转换工具把 OFD 转成 PDF 或 DOCX，再走现有 `parse_pdf_bytes` / `parse_docx_bytes`。

| 维度 | 评价 |
|------|------|
| 文字提取 | ⚠️ 取决于转换器；若转成**图片型** PDF 会丢文字层，反而变差 |
| 依赖 | ⚠️ 强依赖外部二进制（LibreOffice / 金山 OFD 转换 / 数科 OFD 阅读器等） |
| 信创/国产化 | ⚠️ 转换器多为 C++ 二进制，需确认授权与内网部署 |
| 维护 | ⚠️ 多一个外部进程编排与版本管理，故障面增大 |
| 工作量 | 中（引入进程编排 + 失败回退） |

> 不推荐作为主链路：把「已知文字层」的 OFD 转成 PDF 有丢失文字层的风险，得不偿失。

### 方案 D：OCR 兜底（无文字层 OFD）

对无文字层的 OFD 页面转图后 OCR。

| 维度 | 评价 |
|------|------|
| 适用 | 仅无文字层的签章/扫描页（占比低，实测 ~3.3%） |
| 依赖 | OCR 引擎（二期，非瓶颈） |
| 定位 | **兜底**，不是主方案 |

---

## 3. 方案推荐

**推荐组合：方案 A 为主 + 方案 D 兜底（二期）。**

理由：

1. **库优先原则 vs 现实**：用户要求「有成熟库直接用」。但 OFD 读取领域成熟、活跃、许可证清晰（Apache-2.0）、且在内网清华镜像可得的 Python 库**尚未充分验证**。方案 A 用 Python 标准库即可无损拿到文字层，且 OFD 是开放标准（版式 XML 结构公开），自研成本可控、无外部风险。
2. **零依赖最契合当前部署约束**：完全私有化内网、禁止出网、信创适配，纯标准库最稳（无二进制进程编排、无授权、无镜像拉取风险）。
3. **与我们已有能力对齐**：公文「条款/章节」结构识别是本项目自有领域能力（`chunker._section_units`），OFD 只要产出文本 + 页码，即可完全复用现有切分/入库/双粒度链路，不引入新切分逻辑。

**落地动作**：

1. `parser.py` 新增 `parse_ofd_bytes`（zipfile 解包 → `OFD.xml` 定位 Document → 遍历页面 `Text_*.xml` 取文字 → 按页重组），返回 `ParsedDoc`。
2. `_sniff_format` 增加 OFD 识别：看到 `PK` 时**解包探测根 XML 命名空间**，命中 `ofdspec.org` 判为 `ofd`（不能只看魔数）。
3. `parse_bytes` 扩展名分发增加 `.ofd`。
4. 识别无文字层的 OFD 页 → 置 `is_scanned`/`scanned_pages`，与 PDF 扫描件策略一致，二期 OCR 兜底。
5. 其余入库链路（双粒度切分、embedding、密级/权限）无需改动。

> 若后续希望版式/电子签章保真，再评估方案 B（ofdrw）做增强，但那超出「文本入库检索」的核心目标。

## 4. 需要你确认

1. 是否认可「方案 A 为主 + 方案 D 兜底」的组合？（本文为选型文档，选定后我再开发）
2. OFD 是否涉及**电子签章/印章**需要保留/识别？（当前方案只取文字层，印章作为图片资源会被忽略——若需要需单独处理）
3. 是否需要保留 OFD 的**版式元数据**（发文机关、成文日期等）做结构化字段？（现从正文识别，若有结构化 XML 可更准）

## 1. 项目概述

### 1.1 建设背景

企业（含国企、事业单位、大型集团）日常运营中，公文、通知、工作报告、请示、方案、总结、讲话稿等文书是信息传递、决策落地、对外沟通的核心载体。当前普遍存在三类问题：

1. **写得不快**——起草依赖个人经验，从零构思耗时，重复性文书（会议通知、月度报告）反复劳动；
2. **写得不准**——政策依据、历史数据、领导口径、机构称谓难以快速查证，易出现引用过时、表述不统一、数字前后矛盾；
3. **写得不规范**——公文格式、文种选用、政治表述、标点数字用法等存在大量隐性规范，人工把关成本高，出错后影响严肃性。

大模型技术在文本生成、语义检索方面已成熟，但其**通用性与企业所需的准确性、规范性、可追溯性之间存在鸿沟**。本项目以 RAG（检索增强生成）为核心，将企业内部制度、历史公文、政策文件、组织信息与大模型能力结合，构建"**查得到、写得对、合规范、可追溯**"的公文智能写作平台。

### 1.2 项目目标

| 目标类别 | 具体目标 | 衡量指标（建议） |
|---|---|---|
| 效率提升 | 常见公文起草从"小时级"降至"分钟级" | 通知/简报类起草耗时降低 ≥60% |
| 质量提升 | 减少事实性错误与格式错误 | 送审稿一次通过率提升 ≥30% |
| 规范统一 | 格式、称谓、表述符合国标与本单位惯例 | 格式类退回率降低 ≥80% |
| 知识沉淀 | 沉淀组织记忆，降低人员流动带来的经验流失 | 年入库有效语料 ≥[待确认] 万篇 |
| 合规可控 | 内容可溯源、过程可审计、数据不外流 | 生成内容 100% 带引用来源 |

### 1.3 项目范围

**本期范围内（In Scope）**

- 面向公文/通知/报告等文书的**检索增强写作助手**（Web 端为主）
- 企业内部**知识库**（制度、政策、历史公文、模板范文、组织信息）的建设、管理与检索
- **公文模板库**与基于国标（GB/T 9704-2012）的格式套用、导出
- **合规与文字审查**（敏感表述、禁用词、字词规范、事实性引用校验）
- **版本管理、协同编辑、审核流转**与归档
- 与统一身份、OA/IM 的集成对接

**本期范围外（Out of Scope）**

- 通用办公套件（日程、邮箱、即时通讯）的替代
- 电子签章系统的建设（仅做对接）
- 非文书类场景（合同审查、法务、财务分析）——二期评估
- 移动端原生 App（本期以移动端 Web 适配为主）

### 1.4 术语与定义

| 术语 | 定义 |
|---|---|
| RAG | Retrieval-Augmented Generation，检索增强生成。先检索相关知识再交给大模型生成，降低幻觉 |
| 文种 | 公文的种类，如通知、报告、请示、函、纪要等（法定 15 种见附录 A） |
| 套红 | 按规范生成红头文件版式（红头、红线、发文字号、印章位置等） |
| 核稿 | 公文签发前由办公室/秘书处对内容、格式、文字进行的审核环节 |
| 切片（Chunk） | 将长文档切分为便于检索和模型处理的小片段 |
| 重排（Rerank） | 对初检结果做精细相关性打分，提升召回精度 |
| 幻觉 | 模型生成了知识库中不存在或与事实不符的内容 |
| 信创 | 信息技术应用创新，指国产化软硬件生态适配 |

## 2. 业务现状与问题分析

### 2.1 典型写作流程（As-Is）

```
接受任务 → 找范文/找模板 → 找政策依据 → 找数据 → 手工拼装起草
        → 自查格式 → 提交核稿 → 反复修改 → 领导签发 → 编号用印 → 分发归档
```

### 2.2 痛点清单

| 编号 | 痛点 | 影响 | 本项目对策 |
|---|---|---|---|
| P1 | 找范文靠问人、翻共享盘 | 平均耗时 30–60 分钟 | 语义检索 + 范文库（FR-03） |
| P2 | 政策/制度依据版本混乱 | 引用废止文件，风险高 | 知识库版本与时效性标注（FR-02） |
| P3 | 数据指标散落在多个报表 | 数字前后不一致 | 组织记忆库 + 引用溯源（FR-04） |
| P4 | 格式靠肉眼比对 | 反复退回修改 | 模板 + 自动排版校验（FR-05） |
| P5 | 政治表述/禁用词难把关 | 严肃性受损，存在风险 | 规则 + 模型双重审查（FR-06） |
| P6 | 新人上手慢 | 培养周期长 | 模板化引导 + 写作指引（FR-04） |
| P7 | 定稿后知识未沉淀 | 组织记忆流失 | 定稿自动入库（FR-08） |
| P8 | 写作过程无法协同 | 邮件来回传版本 | 在线协同 + 版本管理（FR-07） |

## 3. 用户角色与权限模型

### 3.1 角色定义

| 角色 | 描述 | 核心诉求 | 预估人数 |
|---|---|---|---|
| R1 撰稿人 | 各业务部门起草人员 | 快速出稿、找素材、套模板 | 最多（主体用户） |
| R2 部门负责人 | 处室/部门领导 | 内容把关、修改批示 | 中 |
| R3 公文管理员 | 办公室/秘书处文书 | 格式把关、核稿、编号、模板维护 | 少 |
| R4 知识库管理员 | 知识运营人员 | 语料入库、质量治理、失效下架 | 少 |
| R5 审批领导 | 签发人 | 移动端快速审阅签发 | 少 |
| R6 系统管理员 | IT 运维 | 账号、权限、模型、监控、审计 | 极少 |
| R7 安全审计员 | 合规/保密部门 | 审计日志、违规追溯 | 极少 |

### 3.2 权限模型

采用 **RBAC（角色）+ 数据权限（组织维度）+ 密级（内容维度）** 三维模型：

| 维度 | 说明 |
|---|---|
| 功能权限 | 角色决定可见菜单与可操作按钮（如仅 R3 可发布模板） |
| 数据权限 | 按组织架构树隔离（本部门 / 跨部门 / 全公司 / 指定范围） |
| 密级权限 | 文档标注"公开 / 内部 / 秘密"，用户密级不足则**检索不可见、生成不引用** |

> **关键约束**：RAG 检索必须实现**权限过滤前置**——高密级内容对低权限用户在检索阶段即被过滤，不得进入模型上下文，防止通过对话诱导泄露。这是政务/国企场景的硬要求。

### 4.2 关键用例详述

#### 用例 S1：智能起草（核心主链路）

**前置条件**：用户已登录，具备撰稿权限。

**主流程**：
1. 用户选择文种（通知 / 报告 / 请示 / 函 / 方案 / 总结 / 讲话稿 / 纪要）
2. 用户填写要素表单（标题、主送机关、事由、时间地点、依据文件、关键数据、期望篇幅、语气风格）
3. 系统自动检索：相关政策法规 → 历史同类公文 → 本单位组织信息 → 常用表述
4. 系统生成写作提纲，用户确认或调整
5. 系统按提纲生成初稿，**每个事实性段落附带引用角标**
6. 用户进行多轮对话式修改（"第二部分补充数据""语气再正式些"）
7. 用户点击"格式体检"与"合规审查"，按提示修订
8. 导出 Word / PDF / OFD，或提交审核流程

**异常流程**：
- 3a. 检索无结果 → 系统提示"知识库无相关依据，以下内容为通用生成，请人工核实"，并在成稿中打标
- 5a. 生成超时/失败 → 保留已生成部分，支持续写与重试
- 7a. 审查发现高风险项 → 阻断提交审核，需人工确认豁免

**后置条件**：草稿保存为版本 V1，进入草稿列表。

#### 用例 S5：引用溯源（信任基础）

- 生成内容中每个引用以角标标注，悬浮显示来源摘要，点击跳转原文定位
- 来源标注包含：文件名、发文机关、发文字号、生效日期、密级
- 支持"引用核对"：自动比对生成文本与原文关键数字/表述是否一致
- 若引用文件已废止或被替代，系统显著提示

| 用户行为 | 检索词、生成记录、反馈 | 系统采集 | 中 |

### 7.2 数据实体（核心）

```
KnowledgeBase(知识库) ──1:N── Document(文档) ──1:N── Chunk(切片)
Document ──N:1── DocMeta(元数据：文种/字号/日期/密级/效力)
Template(模板) ──1:N── TemplateField(要素字段)
Article(文稿) ──1:N── ArticleVersion(版本)
Article ──1:N── ReviewComment(批注)
Article ──N:M── KnowledgeRef(引用关系)
Article ──1:1── FlowInstance(流程实例)
User ──N:M── Role ──N:M── Permission
AuditLog(审计日志)
```

### 7.3 数据治理要求

- 入库文档须标注**责任部门与审核人**，明确内容责任
- 建立**失效机制**：新文件发布时自动标记被替代文件为"失效"
- 涉密文档按国家保密规定单独管理，**原则上不进入向量库**
- 用户行为数据脱敏后用于效果分析，保留期 ≤ 2 年

## 9. 技术架构约束与建议

> 本节为推荐方案，最终以技术选型评审结果为准。

### 9.1 架构分层

| 层 | 建议技术 | 说明 |
|---|---|---|
| 前端 | Vue 3 / React + TypeScript | 富文本编辑器可选：OnlyOffice / 协同编辑 SDK / 自研 |
| 应用服务 | Java Spring Boot（或 Python FastAPI） | 业务主链路，微服务拆分 |
| AI 服务 | Python FastAPI + LangChain / LlamaIndex | 编排、RAG、Agent |
| 检索引擎 | Elasticsearch / OpenSearch（关键词）+ Milvus / pgvector（向量） | 混合检索 |
| 重排 | bge-reranker 系列 | 中文效果较好 |
| 生成模型 | Qwen / DeepSeek / GLM（私有化） | 建议 32B–70B 级别起步 **[待确认]** |
| Embedding | bge-m3 / gte-Qwen | 中文语义表示 |
| 存储 | 对象存储（本地文件系统 / S3 兼容）（文件）+ MySQL/达梦（业务）+ Redis（缓存）+ Milvus（向量） | — |
| 部署 | Kubernetes + Docker；支持信创环境 | 私有化交付 |

### 9.2 关键设计约束

1. **检索权限过滤必须前置**，不得依赖模型自觉；
2. **引用溯源为强制能力**，无来源的事实性内容需显著标注；
3. **模型可替换**：通过抽象层隔离，避免绑定单一厂商；
4. **降级设计**：模型不可用时系统仍需提供检索与模板能力；
5. **成本可控**：对高频重复场景引入缓存与结果复用。

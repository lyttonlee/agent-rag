1. 总览

1.1 范围

本文覆盖一篇公文从上传到可被检索/生成使用的完整入库链路，以及链路前端的检索与生成如何消费入库产物。不覆盖：前端交互、认证体系、模板库管理（见《详细功能设计文档》）。

1.3 两条接入路径

路径 入口 适用场景 特点
即时接入 POST /v1/documents/ingest（ingest_document） 第三方公文系统推送结构化正文 同步编排，请求内完成，立即返回 document_id/chunk_count
文件上传 POST /v1/documents/upload（process_ingestion_job） 人工上传 PDF/DOCX 文件 异步入库任务，状态机 PENDING→PARSING→CHUNKING→EMBEDDING→INDEXED/FAILED，前端轮询进度

两条路径共用同一套解析/切分/向量化/落库逻辑（差异仅在编排方式），保证行为一致。

2. 阶段 1：上传与接入

2.1 方案

  • 元数据契约：title / doc_type / issuer / doc_no / publish_date / security_level / permission_tags / space_id / chunk_strategy。文种（doc_type）首批锁定 8 类：通知、通报、报告、请示、函、纪要、决定、意见。
  • 密级与权限在入库时即落库到切片行（chunks.security_level / permission_tags 冗余存储），检索时直接 SQL WHERE 下推，无需 JOIN 文档表。
  • 空间收敛：space_id 缺省归默认空间；无效 ID 直接 404（拒绝写入幽灵空间导致按空间检索丢数据）。
  • 异步任务状态机：每个阶段提交时回写 status + progress（5%→20%→40%→线性到 95%→100%），前端轮询 GET /v1/documents/jobs/{id} 即可呈现进度条。
  • 解析放线程池：parse_bytes 是 CPU 密集型同步调用，用 asyncio.to_thread 执行，避免阻塞事件循环（否则大文档解析期间轮询请求无法被服务，前端表现"卡在解析阶段 5%"——历史实测坑）。
  • 崩溃恢复：启动时 reconcile_stuck_jobs() 把残留非终态任务标记 FAILED，避免"永久 5%"。

2.2 为什么这么选择

  • 密级/权限冗余到切片行是检索性能的关键：权限过滤是每次检索的必做动作，JOIN 文档表会让两路召回 SQL 都变重；冗余的代价是入库时多写两列，换取检索期零 JOIN。
  • 异步任务 + 进度回写而不是同步等待：入库耗时主要在 Embedding（内网 GPU 共享、串行批处理），同步会拖满 HTTP 超时；异步化后第三方可选择轮询或回调。
  • 线程池解析：FastAPI 单事件循环模型下，任何 CPU 密集同步调用都会阻塞全部并发请求。

2.3 优点

  • 第三方接入简单：推元数据 + 文件即可，切分策略/维度/存储细节全部服务端收敛。
  • 失败可观测：任务级 error_message 记录异常类型与前 500 字符，排障不用翻日志。
  • 空间/密级在入口即受控，不依赖调用方自律。

2.4 缺点与权衡

  • 任务在进程内存中运行（asyncio.create_task）：进程崩溃则任务中断（已由启动回收兜底为 FAILED，但任务本身丢失，需重新上传）。多实例部署时任务不共享——当前定位为单进程模块化单体，可接受；若未来水平扩展，需迁移到 Redis 队列（redis_url 配置已预留）。
  • 进度百分比是阶段估值（40%→95% 线性映射），不是真实剩余时间。

3. 阶段 2：原文持久化（对象存储抽象层）

3.1 方案

  • StorageProvider 抽象（app/services/storage.py）：save / get / delete / exists / size 五方法。
  • LocalFSStorage（默认）：原子写（临时文件 + rename）、路径穿越防护（拒绝 ..、绝对路径、根逃逸键）。
  • S3Storage：boto3 惰性导入，指向任意 S3 兼容端点（SeaweedFS / Ceph RGW / 国产对象存储）。
  • 语义统一：content_ref = 存储对象键。local 模式下是相对路径，s3 模式下是对象键，业务代码不感知后端差异。
  • 原文仅在"上游未托管（未传 content_ref）且本次上传了文件"时落库，键为 raw/{doc_id}.{ext}。
  • 当前环境（2026-10-14）已切换为 SeaweedFS（STORAGE_PROVIDER=SeaweedFS，与 s3 等价），实测连通 + 建桶 + 读写一致。

3.2 为什么这么选择

公文原文（PDF 平均 300KB+，20 万文档约 44GB）不适合放 PG；但部署方环境差异大（有的禁容器、有的有国产对象存储），因此存储必须是可替换的抽象层而非硬编码某一家。默认 local 是"零镜像、零协议风险"的保底，s3 是生产推荐。

3.3 优点

  • 部署方自由选择：local（开发/小规模）↔ SeaweedFS/Ceph/国产存储，改一个配置项切换，代码零改动。
  • 路径穿越防护在内，杜绝 ../../etc/passwd 类键。

3.4 缺点与权衡

  • 切换不同步迁移数据：从 local 切到 s3 后，存量文档的 content_ref 在桶里不存在（读取报 FileNotFoundError）。切换时需按相同相对键手工同步（本次环境已提醒并记录）。
  • local 模式无副本/无版本管理，单机故障即丢——生产应使用 s3 模式。

4. 阶段 3：解析

4.1 方案

  • PDF：PyMuPDF（fitz）抽取文本层；is_scanned 标记扫描件（文字层为空或极少）。
  • DOCX：python-docx 抽取段落文本。
  • 嗅探兼容：解析器内含 magic bytes 嗅探，第三方导出文件无扩展名也能解析。
  • 扫描件策略：本期不内置 OCR（种子语料实测 96.7% 有文字层，OCR 非瓶颈）；扫描件标记后由接入方决定是否外挂 OCR 服务回填正文。

4.2 为什么这么选择

公文流转以电子文档为主，文本层覆盖率高；内置 OCR 会引入 PaddleOCR 等重依赖与 GPU 依赖，与"轻量密级控制、内网私有化"的定位不符。保留 is_scanned 标记使后续可插拔。

4.3 优点

  • 解析快（文本层直接抽取，毫秒级）、依赖轻。
  • 无扩展名文件可解析，对第三方导出流友好。

4.4 缺点与权衡

  • 版式噪音：页眉页脚、页码、红头文字会混入文本（依赖后续切分阶段的前缀与结构识别缓解）。
  • 换行拆词（实测坑）：PDF 抽取按行断开词语，如"趸缴"被拆成"趸\n缴"——直接伤害 BM25 关键词路（见 7.4）。建议后续在解析出口做去换行规范化（本轮已验证向量路可兜底）。
  • 扫描件无法自动处理，需人工或外挂 OCR。

5. 阶段 4：切分（重点）

对应代码：app/services/chunker.py；编排：app/services/ingestion.py:_prepare_dual_chunks。

5.1 方案

5.1.1 上下文前缀（性价比最高的一招）

每个切片前置 标题｜发文机关｜日期 前缀。中文公文检索中，用户 query 常含"哪份文件说的"，前缀让每个切片都携带文档级归属信息，显著提升归属类 query 的命中。前缀同时进入 Embedding 与生成上下文，其 token 开销计入切分预算（见 5.1.4）。

5.1.2 四种切分策略（接入方按文种选择）

策略 单元提取 适用
paragraph（默认） 段落/句末边界粗分 最稳妥，尽量不切断语义
section 识别条款标题（第一条/一、/（一）/1./A、…），"标题+其下正文"为整体单元 公文条款级，保留"第X条"结构
sentence 按句末标点切分后合并 问答型检索，保证单句完整
fixed 定长滑动窗口，无视边界 结构稀疏、追求均匀召回

章节结构识别（_SECTION_RE）是本项目自有领域能力——通用切分库只认 Markdown 标题，不认中文公文条款序号。未识别出章节结构时自动回退段落单元，不会把一篇切成"一篇"。

5.1.3 双粒度父子块（small-to-large）

同一套单元提取与 token 计数之上，按两个 token 预算独立切分：

  • 小块（small，默认 100–200 token）：检索单元。入库即 Embedding + tsvector，参与两路召回。
  • 大块（large，默认 800–2000 token）：生成单元。纯文本，不 Embed、不建 tsvector；检索命中小块后按需回表注入生成上下文（见 7.1.4 条件父块注入）。

落库形态：大块先插入并显式指定 ID，小块 parent_id 引用（同事务）；父子挂载 mount_parents 按正文偏移重叠比例启发式完成（小块被父块覆盖的比例评分，零重叠极端 case 退化为"中心距最近"）。两级边界天然错位——挂载追求"父块覆盖小块主体"而非严丝合缝（强行对齐会牺牲边界质量）。

5.1.4 token 预算与 chonkie 的边界

  • 配置单位是 token 而非字符：small_max_tokens / small_overlap_tokens / large_max_tokens / large_overlap_tokens 走配置中心（改库即生效）。
  • 预算覆盖完整切片（正文 + 前缀 + 换行分隔）：前缀是切片的一部分（要 embed、要注入生成上下文），"切片 token 上限"必须是用户看到的那个数。
  • token 计量复用成熟库 chonkie（MIT，Rust 内核）：只用两个能力——count_tokens_batch 批量计数、encode/decode 超长单元硬切。切分逻辑（公文结构识别）自研，通用库不具备该领域能力。
  • chonkie 不可用（内网安装受阻）时退化为字符计数（中文 1 字≈1 token 保守近似），不阻断入库。
  • 尾重叠按单元尾部回填（保持段落/条款完整，不切断），回填后必须仍能容纳新单元，否则放弃回填（保新单元优先）。
  • 单元本身超预算：_token_windows 做 token 窗口硬切（替代字符窗口，与 embedding 模型真实 token 边界对齐）；偏移按 token→字符密度比例估算（启发式，供父子挂载）。

5.2 为什么这么选择

  1. 为什么双粒度而不是单粒度 800 字？ 单粒度面临两难：切大（800 字）→ 向量表示被多主题稀释，检索精度差；切小（150 字）→ 生成上下文碎片化，模型看不到完整条款。small-to-large 让"检索用小块保精度、生成用大块保上下文"，且大块不 embed 使向量/索引体积只随小块增长——这是该模式在单库 PG 上最大的性能红利。
  2. 为什么 token 预算而不是字符预算？ 切分的硬约束是 embedding 模型的上下文窗口（token 计）。字符预算是近似值，遇到中英混排、数字、标号（"（2026）"）偏差明显；token 预算直接对齐模型真实边界，且用户配置的"100–200 token"是真实语义。
  3. 为什么 chonkie 只当 tokenizer？ 通用递归切分库按 Markdown/代码结构工作，对公文条款结构无知；而 tokenizer 是重活（Rust 实现、与 Qwen3 对齐），没有自研必要。库做库擅长的计量，我们做领域擅长的结构——这也符合"不重复造轮子"原则。
  4. 为什么上下文前缀？ 中文公文检索大量 query 带归属意图（"XX 通知里关于资金的要求"）。给每个切片注入文档级身份，是投入一行代码、收益最直接的优化。

5.3 优点

  • 检索精度与生成上下文同时保全，不必二选一。
  • 存储/索引成本可控：向量与 tsvector 只随小块增长；大块仅增文本。
  • 公文条款结构被尊重：section 策略下"第X条"不被打散，引用溯源可定位到条款。
  • 全程 token 计量与模型边界对齐；chonkie 故障可降级，入库主链路不中断。
  • 参数全部走配置中心（19 项检索配置），运营可调无需发版。

5.4 缺点与权衡

  • 小块碎片化：150 token 的小块在条款短的文档（如任免通知）上可能一条一切，检索集合变大、rerank 批处理压力上升（本轮实测 44 片/38s，embedding 吞吐是瓶颈）。
  • 父子错位是常态：两级独立切分，挂载是启发式（重叠比例），边界 case 下父块可能只覆盖小块主体的一部分。
  • 前缀开销：长标题 + 机关 + 日期可能占 30–50 token，小块预算被侵蚀（已通过 overhead 计入预算缓解，但极端长标题仍会压缩正文空间）。
  • 策略需人工选：接入方选错策略（如对法规用 paragraph）会损失条款完整性——默认 paragraph 是稳妥兜底，但不是最优。
  • tokenizer 依赖：chonkie 缺失时退化为字符近似，实际尺寸略偏小（可接受，但非精确）。

5.5 实测数据（2026-10-14，真实政务公文《川办发32号》，7 页/3198 字）

指标 数值
切分结果 小块 44 片 + 大块若干（双粒度）
入库端到端 38.0 s（embedding 吞吐 ≈1.1 片/s 为瓶颈）
原文持久化 312,615 字节落 SeaweedFS（与源 PDF 一致）

6. 阶段 5：向量化与入库

6.1 方案

  • 向量化：ModelProvider(role="emb") 批量调用，_embed_batched 分批（batch=8）+ 有限重试（2 次，退避 2s/4s），逐批回写任务进度。双粒度下仅嵌小块。
  • BM25 索引：入库时即时生成 search_vec = to_tsvector('chinese', content)（zhparser 中文分词）；生产环境另有触发器兜底（迁移 0002），保证 dev/prod 一致。
  • 落库：documents 主表 + chunks 切片表（embedding vector(1024)、search_vec tsvector、security_level/permission_tags/space_id 冗余、granularity、parent_id）。
  • 事务：文档 + 大块 + 小块同事务提交；任一步失败整体回滚，任务标记 FAILED（可重试）。

6.2 为什么这么选择

  • 分批而非整批：内网 embedding 服务（vLLM）对超长输入批响应慢，分批限制单批规模、分摊风险，重试不丢已成功批次。
  • tsvector 入库时生成 + 触发器双保险：dev 直接写值快；prod 走触发器防应用层遗漏。
  • 同事务：避免"文档在、切片缺"的半成品状态。

6.3 优点

  • 入库失败原子回滚，不留脏数据；任务可重试。
  • 进度细粒度（逐批回写），前端进度条真实反映 embedding 阶段。

6.4 缺点与权衡

  • embedding 吞吐是入库瓶颈（本轮实测）：小块策略放大批次数。缓解：调大 small_max_tokens、提高 batch、或多 worker 并发入库（当前为单进程异步）。
  • 向量维度（1024）与模型绑定：更换 embedding 模型须同步 EMBEDDING_DIM 并重建向量索引（启动自检会校验维度一致性）。

7. 阶段 6：检索（重点）

对应代码：app/services/retrieval.py（基础 hybrid_retrieve / 增强 retrieve_enhanced，检索、问答、起草统一走增强入口）。

7.1 方案

7.1.1 主链路：混合检索 → RRF 融合 → rerank → 权限下推

query ──► Embedding(query) ──► ┌ 向量召回: pgvector HNSW, cosine_distance, top-N (small) ─┐
                               │                                                      ├─► RRF 融合(k=60)
                               └ 关键词召回: tsvector @@ plainto_tsquery('chinese'),    │   （按 chunk_id 去重累加）
                                 ts_rank_cd 排序, top-N (small) ──────────────────────┘         │
                                                                                              ▼
                                                          Qwen3-Reranker-0.6B 重排（top-50，截断 1200 字）
                                                                                              │
                                                                                              ▼
                                          密级/权限过滤（build_visibility_filter，服务端 WHERE 下推）
                                                                                              │
                                                                                              ▼
                                                                                    final_top_n（默认 8）Citations

关键细节：

  • 只检索小块：两路召回都显式 granularity='small'——大块无向量/tsvector，不过滤会被 NULL 向量的行污染结果尾部。
  • RRF（Reciprocal Rank Fusion, k=60）：两路各自的排名倒数求和融合。RRF 只用排名不用原始分，天然免疫"余弦距离 0-2 / ts_rank 0-1 / rerank 0-1"量纲不可比问题。
  • rerank best-effort：对 top-N 用 Qwen3-Reranker 逐条打分重排；失败（超时/连接/模型名错/长文 400）自动回退 RRF 顺序，不阻断检索——rerank 是增强排序而非必需环节。
  • rerank 送评前截断（rerank_doc_max_chars=1200）：内网 reranker 上下文 4096 tokens，存量长块超限会被 HTTP 400 拒绝且耗时劣化（实测单篇 3829 字 ≈38s）；公文相关性信息集中在标题与开头，截断到 1200 字把 8 文档批次从 >40s 压到 ~6.5s。
  • 权限/密级下推是服务端 WHERE：build_visibility_filter 把密级比较与权限标签条件编译进 SQL，越权内容根本不进候选集——这是"不能生成后过滤"红线的工程落地（生成后过滤会先泄露给模型）。

7.1.2 弱信号判定（三级兜底的共同触发条件）

_is_weak 任一命中即弱： 1. 结果为空； 2. 双信号异常：向量 top1 距离 > vec_distance_threshold（0.6）且关键词路零命中（与"无有用信息"判定同款保守策略，防单信号误杀）； 3. rerank top1 < parent_inject_min_rerank（0.15）且本次 rerank 真实生效（reranked=True；降级时 RRF 分与 rerank 分不同量纲，不可比，跳过）。

7.1.3 Query 改写重检（P2）

弱信号触发 → rewrite_queries 生成改写变体（四策略，配置中心可选）：

策略 做法
synonym（默认单路） 同义扩展
hyde 假设性答案 embedding 检索
decompose 子问题拆解
auto 双路混合

逐变体检索（受 rewrite_max_rounds 与总超时约束，至少保证完成一轮）→ 候选并集 → 对原 query 重新 rerank（分数同量纲）→ 截回 final_top_n。任何失败/超时保留原结果不阻断。

7.1.4 条件父块注入（P1，变体 B）

改写后仍弱 → 按命中小块的 parent_id 回表取大块，注入生成上下文。四条设计红线：

  1. 权限二次校验：父块查询复用同一 visibility filter（冗余列不替代独立校验，防入库逻辑未来变动引入越权）；
  2. 去重：top_k 个小块常来自同一父块；
  3. 预算：父块数 ≤ parent_inject_max_count、总 token ≤ parent_inject_max_tokens，超预算按相关度截断；
  4. 注入的是完整正文（Citation.content），生成提示词优先用它而非 200 字 snippet——否则注入失去意义。

三级兜底顺序即需求优先级：先改写救回 → 再注入大块补上下文 → 仍不足才拒答/任务型兜底。

7.2 为什么这么选择

  1. 为什么混合检索（BM25 + 向量）而不是纯向量？ 公文 query 两类形态并存：语义型（"资金监管有什么要求"）与专名型（"川府函307号""趸缴"）。专名型是关键词的强项、向量的弱项（罕见词 embedding 区分度低）；语义型反之。两路互补 + RRF 融合，用排名融合避开标度烦恼。
  2. 为什么 zhparser 做中文分词？ PG 内置分词器对中文按单字/双字碎切，plainto_tsquery 产生的查询与 tsvector 难匹配；zhparser 提供词级中文分词，是 PG 生态内零额外组件的方案（相比引入 ES/Jieba 服务，符合"单库统一"架构决策）。
  3. 为什么 rerank 放在融合之后而不是替换某一路？ 两路召回各自 top-N 已覆盖"语义相关 + 关键词命中"两类候选；rerank 用更强模型（cross-encoder）对已缩小的候选集精排，是精度/成本的最优分层。且 rerank 可降级——服务抖动时退回 RRF，主链路永不断。
  4. 为什么权限必须 SQL 下推？ 涉密公文知识库的红线：越权内容不能进模型上下文（进了就可能被吐出来）。生成后过滤 = 先泄露后拦截，形同虚设。WHERE 下推保证"看不见的永远看不见"。
  5. 为什么小块检索 + 大块生成？ 检索精度与上下文完整性不可兼得（见 5.2）；按需回表注入把"取大块"的成本只花在真正命中处，配合预算上限，生成上下文膨胀可控。

7.3 优点

  • 两类 query 形态都覆盖；rerank 精排后 top-1 质量高（本轮实测 top-1 命中率 100%）。
  • 全链路可降级：rerank 失败→RRF；改写失败→原结果；注入失败→仅小块。任何单点故障不阻断检索。
  • 权限/空间过滤全部下推 SQL，密级红线有工程保障。
  • 每步有信号外露（top_vector_distance / keyword_hits / reranked），可观测、可调。

7.4 缺点与权衡

  • BM25 关键词路可能零命中（本轮实测）：PDF 抽取把"趸缴"拆成"趸\n缴"，zhparser 无法匹配。向量路本轮正确兜底（top-1 距离 0.342 命中答案段），但专名型 query 遇上拆词会损失关键词路——建议解析出口做去换行规范化（已知未做）。
  • rerank 绝对分在小语料上扁平（本轮实测 0.015–0.016，无关查询也曾打出 0.8+）：绝对分只能务实取阈值（0.15），不可当概率用；阈值标定依赖评测台（P3）。
  • 延迟构成：embedding(query) + 两路召回 + rerank，本轮实测 2.1s；若触发改写（auto 双路生成 ≈22s）会显著变长——已用总超时预算约束，但弱信号误触发时用户要等。
  • rerank 单点：虽降级不断链，但静默降级时排序质量下降肉眼可见（日志 WARNING 可观测）。
  • 双路索引维护：tsvector 触发器 + 向量索引两套，PG 单库承载（20 万文档 ≈193 万切片、向量 7.9GB 的规模已验证可行，但调优门槛在 DBA）。
